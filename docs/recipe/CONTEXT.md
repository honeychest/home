## 1. 비전과 단계
- 문제: 쇼츠(요리·생활팁)를 재생목록에 저장해두고 필요한 순간에 꺼내지 못한다.
  출발점이 된 말 = "기억해놨다가 필요할때 까먹어야지" — 브랜드 '기까'의 유래(오리지널 문장).
  태그라인(로그인 화면·PWA 설명)은 이 원문을 기반으로 하되, 사용자가 승인한 변형은 허용
  (2026-07-12 확정 — 기존 "변형 금지"는 맘에 안 드는 변형이 쓰였던 것에 대한 규칙이었음.
  현재 로그인 화면 문구 『"기억해놨다가 필요할때 까먹어야지"는 그만, 기까가 꺼내드려요』는 승인됨).
- 장기 비전: 저장한 쇼츠를 필요한 순간에 꺼내주는 앱.
- 1단계(현재): 요리 영역부터. 요리는 "뭐 해먹지"라는 매일 반복되는 트리거와
  냉장고 재고라는 검색 조건이 있어 '꺼내기'가 실제로 작동하는 첫 영역이다.
- 2단계(실사용 검증 후): Android 앱 전환 + 영역 확장 + 중앙 분석 DB 공유
  (영상 ID당 분석 1회, 사용자 개인 DB는 영상 ID + 개인 데이터만 보유).
- 상용화 기획(브랜드 네이밍 '기까/Gikka' 후보, 광고 BM, 계정 동기화 등)은
  아이디어만 존재하는 상태. 2단계 착수 시 별도 문서로 정리한다. 1단계에서는 만들지 않되,
  아래 "확장성 선반영" 절의 데이터 모양만 미리 대비한다.
- 틱톡/릴스 확장은 아이디어가 아니라 확정 기능 (2026-07-11 사용자 확정 — "무조건 한다,
  순서 문제일 뿐"). 유튜브 추출 품질 검증 후 6차로 구현한다 (구현 순서 참고).

## 2. 확정 설계 결정 (2026-07-08 인터뷰)

### 플랫폼·저장
- 형태: 모바일 웹앱. S25 홈화면에 추가해 앱처럼 사용. mac-mini의 home 서비스에서 제공.
- 위치: home 프로젝트에 recipe 도메인으로 추가 (nexus에 넣지 않음 — nexus 비대화 방지).
- DB (2026-07-10 구체화): 이미 가동 중인 PostgreSQL 컨테이너(chs-pgvector, 챗봇 벡터용)에
  `gikka` 데이터베이스를 신설한다. 컨테이너 추가 없음. 전용 계정 `gikka`는 gikka DB만
  접근 가능하게 하여 챗봇 데이터(chs_vector)와 상호 접근을 차단. 기존 DB와 완전 분리.
  (2차 백엔드 단계부터. 이름은 브랜드 '기까'를 따름 — recipe_db 아님)

### 개발 방식 (프론트 우선)
- 프론트를 먼저 완성한다: 백엔드 없이 화면만 만들어 오너가 폰에서 직접 조작하며
  반복 수정하고, "완전해졌다"고 판단한 뒤에 백엔드를 하나씩 연결한다.
- 프론트 단독 기간의 저장은 localStorage. 단, 화면이 저장소를 직접 부르지 않고
  저장소 인터페이스(repository)를 거치며, 데이터 모양은 미래 API 응답과 동일하게 설계한다.
  → 백엔드 연결 = localStorage 구현체를 API 구현체로 교체하는 것으로 끝나야 한다.
- 디자인은 모바일 전용만 만든다 (최종 목표가 앱이므로 데스크톱 대응 불필요).
- 레시피 데이터가 필요한 화면(추천 등)은 손으로 넣은 샘플 레시피로 개발한다.
- (2026-07-10) 냉장고 UI 확인 완료로 프론트 단독 기간 종료 — 백엔드 단계로 전환됨 (아래 구현 순서).
- 프론트 단독(localStorage) 기간은 최소화한다. UI가 확인되면 즉시 백엔드로 넘어간다.
  localStorage 단계가 길어지는 것 자체를 실패 신호로 간주하며, 유실 대비 백업 기능도
  만들지 않는다 (냉장고 데이터는 유실돼도 재입력 가능한 수준). 브라우저는 크롬으로 통일.

### 디자인 체계 (세션이 바뀌어도 단편적 코딩이 나오지 않기 위한 구조)
- 디자인은 recipe 앱만의 새 디자인이다. 기존 home 디자인과 맞출 필요 없음.
- 디자인 방향 (2026-07-09 인터뷰 확정): "냉장고 문 × 프레시".
  - 라이트 기본: 아이스 화이트(살짝 그린 기운) 배경 + 그린(#1f7a3d 계열) 포인트.
  - 메타포: 재료 토글 버튼은 냉장고 자석 스티커(각진 모서리·그림자·ON은 그린 테두리,
    OFF는 점선 회색), 임박 표시는 포스트잇 노랑. 유치해지지 않게 절제해서 실행.
  - 다크 모드: 시스템 설정 자동 전환. "밤의 냉장고" — 어두운 배경에 같은 그린 포인트,
    스티커 메타포 유지.
  - 시안 아티팩트: https://claude.ai/code/artifact/03664dc1-a3d4-41d7-93d6-11f4b1788d15 (마안)
- 폰 접속 경로: 개발 중에는 같은 와이파이에서 PC vite dev 서버 접속,
  1차 완료 시점에 mac-mini home 서비스에 배포해 홈화면 추가(크롬).
- 기술 스택은 기존 frontend(React 19 + Tailwind 4 + shadcn/ui + lucide 아이콘)를 그대로 사용한다.
- recipe 전용 구조:
  - `frontend/src/domain/recipe/style/tokens.css` — 색·간격·글자 크기·모서리 등을
    CSS 변수로 정의한 테마 세트 (라이트/다크 포함). 디자인의 유일한 원본.
  - `frontend/src/domain/recipe/ui/` — recipe UI 킷. shadcn 기반으로 조합한
    공용 컴포넌트(버튼, 목록 행, 카드, 배지, 하단 시트 등)만 여기에 둔다.
  - `frontend/src/domain/recipe/page/` — 화면. 반드시 tokens.css 변수와 ui/ 킷만
    사용해 조립한다. 화면 코드에 임의 색상값·임의 크기 직접 입력 금지.
  - `/recipe/styleguide` 페이지 — 토큰과 ui/ 컴포넌트 전부를 한 화면에 나열.
    새 세션의 AI는 화면을 만들기 전 이 페이지(코드)를 참조하고,
    새 공용 컴포넌트를 만들면 반드시 여기에 등록한다.
- 규칙: 새 화면에서 스타일이 아쉬우면 화면에서 고치지 말고 tokens.css 또는 ui/ 킷을
  고친다 (전 화면에 일괄 반영되도록). 1차 시작 시 tokens.css와 기본 킷부터 만든다.
- 다국어 대비 규칙 (2026-07-09 검수에서 확정): 모든 UI는 글자 길이가 2~3배로 늘어도
  깨지지 않아야 한다. 킷 공통 — 버튼·칩은 줄바꿈 금지+짓눌림 금지(내용만큼 넓어짐),
  탭은 말줄임, 목록 이름은 행 안에서 줄바꿈. 고정 너비 금지, min-height만 사용.
  /recipe/styleguide의 "긴 글자 스트레스 테스트" 절이 검증 장치 — 새 공용 컴포넌트를
  만들면 반드시 여기에 긴 문자열 케이스를 추가한다.
- 언어 계획: 한국어 기본. 영어는 고도화(2단계) 때 i18n 도입으로 추가.
  1단계에서는 레이아웃 내성(위 규칙)과 문구/데이터 분리(PLAYBOOK 품질 기본선)만 지킨다.

### 앱 골격과 홈 화면 (2026-07-09 점검에서 확정)
- 하단 탭 4개: 홈 / 추천 / 냉장고 / 레시피. 1차에서는 냉장고만 동작하고 나머지는 자리만 둔다.
  등록(URL 일괄)은 별도 탭이 아니라 레시피 탭 안의 버튼.
- 홈 화면의 최종 UX: 링크를 복사한 채 앱을 열면 바로 분석이 시작된다.
  - 웹 단계: 브라우저 보안상 클립보드 자동 읽기가 불가하므로 "붙여넣기" 버튼 1탭으로 구현.
  - PWA Share Target 확정 (2026-07-11 사용자 확정 — 후보에서 승격): 유튜브·인스타·틱톡 앱의
    공유 메뉴에서 기까를 선택하면 바로 분석이 시작된다. "나에게 보내기"를 대체하는 핵심 동선.
    3차(등록 화면)에서 구현. 공유 시트 상단 노출은 앱이 강제할 수 없으므로
    오너가 설치 후 공유 시트에서 기까를 길게 눌러 고정(pin)하는 것으로 해결.
  - 2단계(네이티브 앱): 앱 실행 시 클립보드 자동 감지로 승격.
- 홈에는 최근 분석된 쇼츠 섬네일 목록을 표시한다 (레시피 데이터가 생기는 2~3차에서 구현).
- 앱 표시명은 '기까'. 최소 PWA manifest(이름·아이콘·전체화면)를 1차에 포함해
  홈화면 추가 시 앱처럼 뜨게 한다.

### 인증 (2026-07-10 확정)
- Google 로그인 사용. 도입 시점은 4차(백엔드 연결) — 프론트 단독 기간(1~3차)은 로그인 없음
  (localStorage는 그 브라우저 전용이라 무인증으로 충분. 검증할 서버도 없음).
- 사용자 열쇠 = Google 계정 ID(sub). 2단계 계정 동기화·중앙 DB의 기반이므로
  4차 데이터 모양에 처음부터 포함한다.
- 구현: 프론트 GIS(Google Identity Services) 버튼 → ID 토큰 → 백엔드 서명 검증 →
  recipe 자체 세션 발급. `/api/recipe/**` 전용 SecurityFilterChain을 recipe 패키지 안에 두고
  기존 `global/config/SecurityConfig.java`는 건드리지 않는다 (분리 규율).
- OAuth 클라이언트는 Gemini용 결제 미연결 구글 프로젝트에 recipe 전용으로 생성
  (OAuth는 결제 불필요 → 무료 등급 소멸 위험 없음). 기존 home 로그인 계정과 완전 무관.
- 다중 사용자 기본 설계 (2026-07-10 확정): 누구나 구글 로그인해 쓰는 것이 최종 목표.
  모든 데이터는 사용자 소속(userId 필수), 냉장고·레시피·통계 전부 계정별 분리.
  단 1단계 동안은 허용 목록 스위치(설정의 이메일 목록)를 켜서 오너 계정만 통과 —
  공개 전까지 타인의 Gemini 무료 한도 소모·서버 자원 사용을 차단. 공개 시 스위치만 끔.
- 세션: 서명 토큰(JWT) HttpOnly 쿠키(30일, SameSite=Lax, Path=/api/recipe) —
  앱 2인스턴스 환경에서 서버 상태 없이 검증 가능. 서명 키는 gikka DB에 첫 기동 시
  자동 생성·보관 (서버 .env 추가 불필요, 인스턴스 간 공유).

### 시간 기준 (2026-07-10 확정)
- 날짜 판정(선반 14일·스테퍼 미래 금지)의 기준은 사용자 기기의 오늘 — 이미 프론트(fridgeShelves)가 담당.
- 등록일 기록만 서버 LocalDate.now() (1단계는 한국 단일 시간대라 충분. 서버 컨테이너 TZ=Asia/Seoul 전제).
- 2단계 글로벌 공개 전에 등록 API가 클라이언트의 오늘 날짜를 받도록 전환한다
  (그때 "미래 날짜 금지"의 시간대 허용 오차 규칙을 함께 정한다). 데이터 모양(DATE)은 시간대 중립이라 스키마 변경 없음.

### API 에러 계약 (2026-07-10 확정)
- `/api/recipe` 응답의 계약은 HTTP 상태 코드뿐이다. 사용자에게 보여줄 문구는 프론트가 소유한다.
  (백엔드 ResponseStatusException 메시지는 로그·디버깅용 — 스프링 기본 설정상 응답 본문에 실리지 않음)
- 프론트 처리 위치: 세션 만료(401)는 http.ts 공용 seam(로그인 화면 전환),
  그 외 조작 실패 문구는 화면의 조작 실행기(runMutation — FridgePage 패턴) 한 곳에서.

### 확장성 선반영 (데이터 모양에만 — 1단계 UI에는 노출하지 않음)
2단계(영역 확장·멀티 플랫폼·중앙 DB)에서 스키마를 갈아엎지 않도록,
저장 데이터와 저장소 인터페이스(미래 API 응답) 모양에 다음 필드를 처음부터 포함한다:
- `platform`: 영상 출처. 1단계에서는 항상 YOUTUBE (향후 TIKTOK, REELS 등 추가).
- `category`: 영상 분류. RECIPE/TIP/ETC 3종을 분석이 판정·저장 (2026-07-12 변경 —
  구 "1단계 항상 RECIPE 고정"을 대체. 2단계에서 TRAVEL, EXERCISE, DIY, STUDY 등으로 세분화).
  1단계 기능은 RECIPE 만 사용 — TIP/ETC 는 저장만.
- `summaryVersion`: AI 요약 버전 번호. 추출 모델·프롬프트 세대가 바뀌면 번호를 올리고,
  구버전 요약만 골라 재생성할 수 있게 한다.
이 필드들은 1단계 화면·기능에 어떤 동작도 추가하지 않는다 (값 고정 저장만).

  - 신선 선반만 최신순 정렬(새것이 왼쪽) — 방금 넣은 재료가 스크롤 없이 바로 보이게.
    임박·오래됨 선반은 오래된 순(왼쪽=급한 것) 유지.
  - 버튼은 있음/없음 토글이다: 탭하면 등록(등록일 오늘), 다시 탭하면 없음 처리.
    장 보고 와서 산 것들을 탭탭탭 하는 것이 기본 사용 흐름.
  - 첫 사용을 위해 한국 가정 상비 재료 12개를 시드로 심는다.
    실제 추가 횟수가 쌓이면 순위가 사용자 것으로 자연 교체된다.
  - 표시 순서(2026-07-09 검수에서 확정): 자주 사는 재료는 화면 진입 시 1회만 정렬.
    조작 중에는 재정렬하지 않는다 (누른 버튼이 자리를 옮기면 연타가 불편).
    라벨의 표시 개수는 FREQUENT_LIMIT 상수와 연동 (현재 12, 확장 가능).
  - 편집 모드(2026-07-09 검수에서 추가): "편집" 버튼으로 자주 사는 재료 목록에서
    원치 않는 재료(오타 등)를 직접 제거할 수 있다. 제거해도 냉장고 안 재료에는 영향 없음.
    제거된 재료(시드 포함)는 숨김 처리되어 다시 안 올라오되, 직접 입력으로 재추가하면 해제.

### 추천
- 2층 구조: 1층 "지금 만들 수 있어요" 최대 5개 / 2층 "하나만 사면 돼요" 최대 3개(+살 재료 표시).
- 정렬: 임박 재료 사용 레시피 최상단 → 그다음 오래된 재료 사용 순.
- 계산: 재료 태그 집합 비교. LLM 사용 안 함 (추천은 비용 0, 즉시 응답).
- 상세: 재료 + 요약 단계 + 원본 영상 링크.

## 3. 분리 규율 (앱 전환 대비 — 반드시 지킬 것)
1. 코드 격리: 백엔드는 `domain/recipe` 패키지 안에서만. 다른 도메인과 상호 참조 금지.
   프론트는 `frontend/src/domain/recipe/`에 격리.
2. DB 격리: recipe 전용 데이터베이스 + 전용 접속 설정. 기존 테이블과 외래키·조인 금지.
3. API 격리: 경로 `/api/recipe/**` 통일.
4. AI 호출 격리: Gemini 호출을 인터페이스 뒤에 숨김 (URL 프리뷰 정책 변경 시 구현체만 교체).
5. 설정 격리: recipe 관련 설정(API 키 등)은 별도 설정 그룹으로.
6. 격리 자동 감시 (2026-07-10 확정): ArchUnit 테스트로 `domain.recipe` ↔ 다른 도메인의
   상호 import를 빌드 단계에서 차단한다. 4차 백엔드 착수 시 첫 작업으로 작성 —
   규율을 사람 기억이 아니라 테스트가 지키게 한다.
7. 공용 코드 허용 목록: 없음 (2026-07-10 확정). 기존 home의 공용 유틸·설정이 필요하면
   recipe 패키지 안으로 복사해 소유한다 (앱 분리 시 함께 들어내기 위해).
8. DB 접속 격리: recipe 전용 DataSource(전용 접속 설정)를 둔다. 기존 DataSource 재사용 금지.

## 4. 구현 순서 (2026-07-10 재편 — 백엔드 우선으로 전환)
재편 이유: 냉장고 UI 검수·배포·홈화면 추가가 완료되어 프론트 단독 기간의 목적이 달성됨.
샘플 레시피로 화면을 먼저 만드는 구 2·3차는 버리는 작업이며, 최대 불확실성인
Gemini 추출 품질을 먼저 검증하는 순서가 낫다 (localStorage 최소화 원칙과도 일치).
레시피·추천 UI는 실제 추출 데이터가 생긴 뒤에 만든다.

1차: 디자인 기반 + 앱 골격 + 냉장고 화면 — 완료 (2026-07-10 배포, 홈화면 추가 확인)
2차: 백엔드 기반 — PostgreSQL recipe 전용 DB + 전용 DataSource, ArchUnit 격리 감시,
     Google 로그인, /api/recipe API, 냉장고 저장소 교체.
     성공 기준: 냉장고 화면 코드 무수정으로 저장소 구현체만 교체됨.
3차: Gemini 추출 + 등록 화면 (URL 개별 + 재생목록 일괄, 대기열) — 추출 품질 검증 지점.
     PWA Share Target 등록 포함 (공유 메뉴 → 기까 → 즉시 분석).
     (2026-07-11 조사) 최신 Gemini는 media_resolution 파라미터로 프레임당 토큰을 조절 가능 —
     쇼츠는 저해상도로 시작해 품질 부족 시에만 올린다 (무료 한도 절약).
     요청당 영상 10개까지 가능하나 품질·오류 격리를 위해 1영상 1요청 원칙 유지, 필요 시 재검토.
     대기열은 DB 테이블(대기/분석중/완료/실패) + 단일 워커로 구현 — 별도 큐 인프라 없음.
     병목은 Gemini 분당 한도이므로 다중 사용자가 돼도 같은 구조를 유지한다.
4차: 레시피 목록·상세 + 추천 화면 (샘플이 아닌 실제 추출 데이터로)
5차: 다듬기 (자주 사는 재료 버튼 실동작, 새 재료 분류 질문, 진행률 다듬기)
6차: 릴스·틱톡 확장 (2026-07-11 확정) — 착수 조건은 유튜브 추출 품질 합격뿐.
     방식: 서버에서 yt-dlp로 영상 다운로드(임시, 분석 후 삭제) → Gemini File API 업로드 →
     기존 추출 프롬프트 재사용. 규율 4의 추출 인터페이스에 platform별 구현체만 추가
     (스키마·화면 변경 없음 — platform 필드 선반영 덕분).
     첫 작업: yt-dlp로 본인 릴스·틱톡 링크 실제 다운로드 테스트.
     인스타 쿠키 운영 방식 (2026-07-11 확정 — 무인 운영 목표, 유료 서비스 안 씀):
     - mac-mini 크롬에 인스타 전용 프로필을 만들어 로그인 유지,
       yt-dlp는 --cookies-from-browser chrome으로 그 프로필에서 쿠키를 직접 읽음
       (쿠키 파일 내보내기·수동 갱신 단계 자체를 제거. 첫 실행 시 macOS 키체인 접근 허용 1회 필요).
     - 세션 유지: launchd 주 1회 `open -a "Google Chrome" --profile-directory=... instagram.com`
       으로 페이지만 터치 (진짜 크롬·진짜 프로필이라 봇 탐지 불가).
     - 유효성 체크는 사용 직전 + 일 1회. 매분 체크 금지 — 기계적 반복 접근이 봇 신호가 되어
       쿠키 수명을 오히려 줄임. 실패 시 텔레그램 알림 → 사람은 재로그인만 (드묾).
     - 로그인 자동화(아이디·비번 스크립트 입력) 금지 — 봇 탐지 최우선 표적, 계정 정지 위험.
       Playwright/Selenium으로 브라우저 조종도 같은 이유로 안 씀 (자동화 지문 감지됨).
     참고 구현: github.com/pickeld/social_recipes — 동일 문제·동일 파이프라인(yt-dlp→LLM)의
     오픈소스. 쿠키 관리가 심하게 귀찮아지면 Apify류 유료 스크래핑이 대안(개인용엔 과함).

## 5. 리스크 (인지한 상태로 진행)
- Gemini URL 기능은 프리뷰: 정책 변경 시 yt-dlp 다운로드+업로드 방식으로 교체 (규율 4로 대비).
- 추출 품질 미검증: 5차에서 검증. 부족하면 프롬프트·해상도 조정 → 그래도 안 되면 유료 모델 소액(영상당 10~15원) 재논의.
- 유튜브가 유사 기능 출시 가능성: 개인 도구 가치는 불변. 상용화 판단 시점에 재평가.
- 무료 등급 한도: 일 약 250~1,500요청, 분당 약 10요청, 유튜브 URL 일 8시간 분량.
