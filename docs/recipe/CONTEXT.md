# recipe — CONTEXT (유일한 진입점 · 확정 결정만)

> 새 세션은 이 문서를 읽는 것으로 시작한다. 여기엔 **지금 유효한 결정만** 적는다.
> 왜 그렇게 정했는지(계기·실측·번복 이력·기각된 대안)는 `DECISIONS-LOG.md` —
> **결정을 뒤집으려 할 때만** 연다. 진행 상태의 유일한 원본은 `progress.html`.

## 0. AI 작업 지침 (매 세션)
- 작업 전: `progress.html` "다음 세션이 이어서 할 일" + `PLAYBOOK.md`(공통 규칙 + 현재 단계).
  새 단계 착수는 grill-me 점검이 끝나기 전에 시작하지 않는다.
- 작업 후(중단 시에도): `progress.html` 체크리스트·다음 할 일·갱신일 갱신.
- 이 문서는 결정이 바뀔 때만 고친다. **새 결정 = 여기 한 줄, 경위 = DECISIONS-LOG.md 맨 아래.**
  진행 상태를 여기 중복 기록하지 않는다. `progress.html` 의 "지금 알아야 할 것" 최상단은 항상 사용자 액션.
- 쓰기·삭제·편집·생성은 '승인' 필요. 예외: `docs/recipe/` 문서 4종(CONTEXT·PLAYBOOK·progress·DECISIONS-LOG)
  갱신은 사전 승인된 것으로 본다.

## 1. 비전과 단계
- 문제: 쇼츠(요리·생활팁)를 저장해두고 정작 필요한 순간에 못 꺼낸다. 브랜드 '기까'의 유래 =
  "기억해놨다가 필요할때 까먹어야지". 태그라인은 이 원문 기반, 승인된 변형 허용.
- 1단계(현재): 요리 영역. 2단계: Android 앱 전환 + 영역 확장 + 중앙 분석 DB 공유
  (영상 ID당 분석 1회, 개인 DB는 영상 ID + 개인 데이터만).
- 틱톡/릴스 확장은 확정 기능(순서 문제일 뿐) — 6차.
- 상용화 기획(네이밍·광고 BM·계정 동기화)은 아이디어 상태. 2단계 착수 시 별도 문서.

## 2. 플랫폼·저장·개발 방식
- 형태: 모바일 웹앱(PWA), mac-mini 의 home 서비스에서 제공. home 프로젝트에 recipe 도메인으로 추가.
- DB: 기존 PostgreSQL 컨테이너(chs-pgvector)에 `gikka` 데이터베이스. 전용 계정 `gikka` 는 이 DB 만 접근.
- 디자인은 모바일 전용만 만든다. 브라우저는 크롬 기준.
- 프론트 단독(localStorage) 기간은 종료됨 — 지금은 백엔드 연결 완료. 저장소는 인터페이스(`data/*Repository`) 뒤에.

## 3. 디자인 체계
- recipe 만의 디자인. 방향 = "냉장고 문 × 프레시": 아이스 화이트 배경 + 그린(#1f7a3d 계열) 포인트,
  재료 토글은 냉장고 자석 스티커, 임박은 포스트잇 노랑. 절제해서 실행.
- **다크 모드 없음** — 시스템 설정과 무관하게 라이트 톤 하나(tokens.css 에 dark 블록 없음).
- 구조: `style/tokens.css`(디자인의 유일한 원본) / `ui/`(공용 킷) / `page/`(화면 — 토큰과 킷만 조립,
  임의 색상값·크기 직접 입력 금지). 스타일이 아쉬우면 화면이 아니라 토큰·킷을 고친다.
- `/recipe/styleguide` = 토큰·킷 카탈로그. 새 공용 컴포넌트는 여기 등록 + 긴 글자 스트레스 케이스 추가 의무.
- 다국어 대비: 글자가 2~3배 길어져도 안 깨진다. 버튼·칩은 줄바꿈 금지+짓눌림 금지, 탭은 말줄임,
  목록 행 이름류는 최대 2줄+말줄임(line-clamp), 우측 상태값은 고정 최소폭. 고정 너비 금지(min-height 만).
- 배지 색: 전부 같은 파스텔 칩 모양이고 의미는 색으로만 구분. 두 팔레트를 절대 혼용 금지 —
  (1) 카테고리 cat-1~8 고정 순서(1 레시피·2 유틸·3 기타, 4~8 예비 — **순서 변경 금지**),
  (2) 상태 neutral/analyzing/good/warning/serious/critical. 새 색은 dataviz 스킬 `validate_palette.js`
  로 색맹 구분성·명도·채도를 실측 검증(눈대중 금지).
- 하단 시트(RcpBottomSheet): 최대 70% 높이(위 30%는 배경 노출→탭으로 닫기), 헤더를 아래로 쓸어내리면
  닫힘(60px). X 버튼 안 씀. `.rcp-sheet` 에 `overscroll-behavior-y: contain`.
- 색을 바꾸면 CSS 변수를 못 읽는 정적 파일 2곳도 함께: `public/recipe/manifest.webmanifest`, `public/recipe/icon.svg`.

## 4. 앱 골격
- 하단 탭 4개: 홈 / 추천 / 냉장고 / 보관함.
- **예외 — 운영자 모드**: `/recipe/monitor/*` 에서만 오너 전용 탭(대기열 / 사전 / 나가기)으로 통째 교체.
  [나가기]는 항상 홈으로. 탭 바를 두 벌 만들지 않고 `RcpTabBar` 가 `tabs` 를 주입받는다(기본값=4탭).
- 홈: 최근 분석 완료 영상 섬네일 줄(분류 무관 DONE, 개수 상수 `RECENT_LIMIT`) + X(트위터) 영상
  다운로드(오너용 1회성, 기록 없음) + 계정 시트(헤더 우측). 유튜브 등록은 보관함 탭 FAB 이 전담.
- 입력창에 붙여넣으면(`onPaste`) 즉시 분석 — [등록] 버튼을 또 누르지 않는다. 버튼은 직접 타이핑용으로 유지.
- **PWA Share Target**: 유튜브·인스타·틱톡 공유 메뉴에서 기까 선택 → 즉시 분석(핵심 동선).
- 앱 표시명 '기까'. manifest + 서비스워커(캐싱 없는 pass-through — 완전한 standalone 설치 요건).
- 설치 안내 시트: 크롬은 `beforeinstallprompt` 가로채 [설치하기], iOS 는 안내 영상 + 텍스트 요약.
  재노출은 "띄운 시각" 기준 6시간(닫기/설치 구분 없음, 이미 설치면 standalone 판정으로 안 뜸).

## 5. 인증
- Google 로그인. 사용자 열쇠 = 구글 계정 ID(sub). 모든 데이터는 userId 소속(계정별 완전 분리).
- 프론트 GIS 버튼 → ID 토큰 → 백엔드 서명 검증 → recipe 자체 세션(JWT 30일, 서명 키는 gikka DB 에 자동 생성).
- **세션 전달은 `Authorization: Bearer` 헤더**(쿠키 아님) — 오리진 무관하게 동작(네이티브/TWA 대비),
  브라우저가 자동 첨부하지 않아 CSRF 도 구조적으로 차단(그래서 CSRF 토큰 비활성).
  프론트 `data/tokenStorage.ts` 포트 + `http.ts` 의 `authHeader()`. 백엔드 `JwtCurrentUser`.
  CORS 는 `gikka.auth.allowed-origins`(기본 비어있음 — 네이티브 오리진이 정해지면 채움).
- `/api/recipe/**` 전용 SecurityFilterChain 을 recipe 패키지 안에 둔다(기존 `SecurityConfig` 불변).
- OAuth 클라이언트는 결제 미연결 구글 프로젝트에 recipe 전용으로 생성(무료 등급 소멸 방지).
- 허용 목록(`gikka.auth.allowed-emails`)은 **현재 비어 있음 = 전체 공개 상태**. 오너 판정
  (`GikkaAuthProperties.isOwner`)은 이 목록 재사용 — 목록이 비면 오너 전용 기능은 아무도 못 본다.
  공개 상태에서 관리자 판정이 필요해지면 그때 새로 설계해야 한다.

## 6. 계약·기준
- **API 에러 계약**: `/api/recipe` 응답의 계약은 HTTP 상태 코드뿐이다. 사용자 문구는 프론트가 소유.
  프론트 처리 위치 — 401은 `http.ts` 공용 seam(로그인 전환), 그 외 조작 실패 문구는 화면의 `useMutation`.
  상태코드 구분: 400 링크 형식 오류 / 404 비공개·삭제 영상 / 409 중복 / 503 조회 자체 실패(재시도 유도).
- **시간 기준**: 날짜 판정(선반 14일·스테퍼 미래 금지)은 사용자 기기의 오늘(`fridgeShelves`).
  등록일 기록만 서버 `LocalDate.now()`(TZ=Asia/Seoul 전제). 2단계 글로벌 공개 전에 클라이언트 날짜를
  받도록 전환한다(스키마 변경 불필요 — DATE 는 시간대 중립).

## 7. 등록·분석 파이프라인
- 등록: 재생목록 URL 일괄 + 링크 개별. 자동 동기화 없음. 링크에 영상+재생목록이 같이 있으면 **영상 1개 우선**
  (일괄은 재생목록 자체 링크로만). 분기 판정의 단일 원본 = 프론트 `data/registerLink.ts`.
- 고유 열쇠 = 영상 ID(다양한 링크 형태에서 ID만 추출해 중복 판별).
- 2단계 공개 시 일반 사용자 메인 동선은 [내 재생목록 불러오기](OAuth `youtube.readonly` — 민감 스코프라
  구글 앱 심사 필수, 2단계 초반에 신청). 공유/붙여넣기는 보조 동선으로 유지 + 안내물 제작.
- 파이프라인: ① 메타 조회(제목·섬네일·길이·설명란) → ② 7분 초과(`MAX_VIDEO_MINUTES`)는 분석 안 함
  ("너무 김", 등록 즉시 사용자에게 알림) → ③ 1회 호출로 분류+추출 → ④ 실패 처리.
- 분류: RECIPE(요리) / TIP(생활팁) / ETC. RECIPE 는 재료·단계 추출, TIP·ETC 는 요약 2~3문장.
  **전 분류 공통으로 검색용 태그 저장**(검색 기능 자체는 나중). 1단계 기능은 RECIPE 만 사용.
- 분석 입력 우선순위: **설명란·제목 표기가 음성보다 우선**(상품명·요리명은 STT 오인식 위험).
  설명란에 재료가 있으면 원문 그대로 사용, 없는 것만 화면·음성으로 보완. 재분석·REMOVED 복구 시
  메타(제목·썸네일·길이·설명란)도 다시 조회해 갱신한다.
- 재료는 **추출 원문 그대로 저장**(정규화는 사전이 담당 — 9절).
- 실패 처리: 일시적 실패(`TransientFailureException` — 429·503·타임아웃)는 시도 횟수 안 깎고 60초 후
  자동 재개, 그 외(파싱 실패 등)는 3회 후 FAILED + 수동 재분석. 실패 사유는 `video.last_error` 에 저장.
- **모델·키**: Gemini(AI Studio 신형 키 `AQ.`)와 YouTube Data API(구형 `AIza`)는 키가 따로다(겸용 불가).
  `GIKKA_GEMINI_API_KEY` + `GIKKA_YOUTUBE_API_KEY`. 모델 `gemini-3.5-flash` 고정 +
  404(모델 폐쇄) 시 `gemini-flash-latest` 자동 전환(재기동 전까지) + 텔레그램 알림.
  latest 상시 사용 금지(품질이 소리 없이 바뀜). 무료 등급 사용, 해당 프로젝트에 **결제 연결 금지**.
- 추출은 Gemini 에 유튜브 URL 직접 전달(영상 다운로드 없음). 일괄 등록은 대기열(분당 한도 맞춰 순차).
- 등록 시점 차단: 비공개·삭제·잘못된 ID(메타에 아예 없음) = 404 로 등록 거부 / 조회 호출 자체 실패
  (HTTP·네트워크·타임아웃) = 등록 허용(순간 장애로 멀쩡한 영상을 영구 거부하면 안 됨). 이 둘을 뒤섞지 말 것.
- 비-오너의 재생목록 일괄 등록은 한 번에 10개까지(`PLAYLIST_LIMIT_FOR_NON_OWNER`). 오너는 예외.
- 분석 중 서버 재시작 복구: 워커가 5초마다 `requeueStale()` — ANALYZING 10분 초과를 WAITING 으로 되돌림.

## 8. 로컬 모델 페일오버 (구현 완료)
- **라우팅**: 로컬이 먼저 분류+추출 → `category==RECIPE` 면 그 결과 채택(Gemini 호출 안 함, 한도 절약).
  RECIPE 가 아니면(TIP/ETC) 로컬 결과를 버리고 Gemini 재분석(할루시네이션 회피).
  로컬 파이프라인 자체가 불가하면 전체 Gemini 폴백. `HybridRecipeExtractor`(@Primary)가 담당.
- **Gemini 검증이 일시적 실패(429·503·타임아웃)면 로컬 TIP/ETC 결과를 1회만에 채택**해 완료 처리
  (재시도 없음). 대체할 로컬 결과가 없으면 기존 60초 백오프 루프. `gemini_retry_count`(V10) 로 노출.
- 입력: yt-dlp 다운로드(임시) → ffmpeg 프레임 + 16kHz 모노 오디오 → whisper.cpp STT →
  프레임+전사+설명란+제목을 로컬 비전 모델에 전달.
- **STT 모델 = whisper.cpp large-v3-turbo**(base·medium 은 기각 — 한국어 오인식·비한국어 붕괴).
- **`TARGET_FRAMES` = 24**(12에서 상향) — 프레임 수가 로컬 추출 품질의 진짜 지렛대다. 24에서 표기
  정확도·환각·비결정성이 모두 개선됐다. 약 25초 미만 영상은 간격 하한(`MIN_FRAME_INTERVAL_SECONDS`=2)
  때문에 영향 없음. 품질 실험은 `gikka-extractor/server.py` 를 모듈로 import 해 상수만 바꿔 직접 호출.
- **호스트 서비스**: Spring 은 도커(Alpine/aarch64)라 yt-dlp·ffmpeg·whisper 를 직접 못 돌린다 →
  mac-mini 호스트에 상시 HTTP 서비스(`gikka-extractor/server.py`, 표준 라이브러리만) + launchd,
  Spring 은 `host.docker.internal:8765` 로 호출만. 배포·설정은 `gikka-extractor/README.md`.
- LM Studio 는 **"Mac-mini-LLM" 별칭**으로 호출한다 — 로드된 모델이 뭐든 잡혀서 모델 교체 시 재배포 불필요.
- **사본 금지(사고 재발 방지)**: launchd 는 체크아웃의 `gikka-extractor/server.py` 를 직접 실행하고
  Jenkins `Deploy Gikka Local` stage 가 재기동한다. **`cp server.py ~/gikka-local/` 를 다시 만들지 말 것** —
  손으로 뜬 사본이 조용히 어긋나 DONE 125건의 품질 경고가 한 번도 작동하지 않은 사고의 원인이었다.
  `~/gikka-local` 에는 모델·로그만 둔다. plist 최초 설치 1회만 손이 필요하다.
- 참고: mac-mini 의 `~/.hermes/` 는 사용자의 별개 개인 시스템 — 건드리지 않는다.

## 9. 분석 품질·재료 사전
- **품질 경고는 "하나도 없음"만**(`data/analysisQuality.ts` 순수 함수, DB 컬럼 없음): 재료 0개 또는
  조리순서 0개 → "재료를 하나도 못 찾았어요". 보관함 카드 `확인 필요` 배지 + 요약줄 필터.
- **재료 개수 임계값("N개 이하면 의심")은 만들지 말 것** — 실측 결과 재료가 적은 게 정답인 라면·간단
  요리가 대부분이었다. 개수는 틀렸다는 증거가 못 되고, 오탐은 경고 피로를 만든다.
- "steps 에 나온 재료가 ingredients 에 없음" 판정은 사전 기반으로만 한다 — 키워드를 손으로 박아 흉내내지 말 것.
- **사전 스키마**(`(name, match_key, status)`, 이름 1개당 1행):
  - `status` 5종: PENDING / SKIPPED / CONFIRMED_MAIN / CONFIRMED_SEASONING / CONFIRMED_BASIC.
    **양념 여부의 단일 원본은 status 하나다**(tier 컬럼 없음 — 파생을 컬럼으로 두지 않는다).
  - 매칭이 읽는 양념 집합 = `status='CONFIRMED_SEASONING'`. 그 외는 전부 **주재료 취급**(안전 기본값).
  - `match_key` = "무엇이 있으면 이걸 가진 걸로 칠까". 기본값 = 자기 이름(안 묶으면 엄격 매칭 그대로).
    냉장고 이름과 레시피 이름의 `match_key` 가 같으면 "있음".
  - **멤버의 성격은 대표가 정한다**(양념 여부 = 대표의 status, 자기참조 조인). 멤버 status 는 안 지운다 —
    그룹을 풀면 원래 판정이 돌아온다.
  - **그룹 깊이는 항상 1** (A→B→C 금지 — `merge()` 가 평탄화. 순환도 이 평탄화로 안 생김).
- **안전 비대칭 규칙**: 쪼개기(match_key=자기자신)는 자동/안전. **묶기는 오너 확정 또는 PENDING 자동 판정만** —
  이미 오너·과거가 판정한 것은 불가침. 오병합(진간장≠간장, 맛소금≠소금, 파프리카≠파)이 사람 손 없이 안 일어남.
- **자동 판정 파이프라인**(RegistrationWorker, RECIPE 분석 직후 — **순서가 곧 규칙**):
  1) 신규 재료 PENDING 등록 → 2) 수량·단위 변형 자동 병합(`representativeCandidate`, 기계적으로 확실한 것만)
  → 3) 확신 양념 자동 승격 → 4) PENDING 전체 AI 자동 판정(`IngredientAutoJudge`, 로컬 우선·Gemini 폴백).
  **2)가 3)보다 먼저여야 한다** — 순서가 바뀌면 "간장 2큰술"이 CONFIRMED 가 돼 병합 가드에 걸려 영영 홀로 남는다.
  어떤 실패도 영상 분석을 실패시키지 않는다(조용히 건너뜀). 반영 내역은 `ingredient_change_log`(V14, append 전용)
  → 사전 화면 [자동 반영] 시트. 오너의 역할은 사전 승인이 아니라 **사후 감사**다. 알림은 두지 않는다.
- **사전 판정 규칙의 단일 원본 = `DictionaryJudge`**(2026-07-25). 셋을 소유한다: 판정 대상 선정
  (PENDING 대표만 / 전체 대표는 mergeInto 참고용) · 채널 라우팅 · 제안 검증(지어낸 이름·없는 대표·
  체인·이미 판정된 것 거르기). 채널은 `IngredientJudge` 시임 뒤 어댑터 2개(Gemini `IngredientAuditor` /
  로컬 `LocalIngredientAuditor`)이고, 제안 어휘·응답 파싱도 시임이 소유한다.
  **추출(`RecipeExtractor`+@Primary `Hybrid`)과 달리 @Primary 라우터 빈이 없다** — 순서가 호출부마다
  반대라서다: 상시(워커)=`LOCAL_FIRST`(무료 한도 절약) / 온디맨드(오너 [AI 점검])=`GEMINI_FIRST`(품질 우선).
  두 채널이 다 막히면 **1차 채널의 예외를 그대로** 던진다 — 컨트롤러의 503 매핑이 그 타입에 걸려 있다.
  모듈 밖에 남긴 둘은 청중이 달라서다: **적용**(워커만 한다) 과 **실패 정책**(워커=조용히 삼킴 /
  컨트롤러=503). 이전엔 이 규칙이 워커·컨트롤러에 한 벌씩 두 벌이었고 이미 미세하게 갈라져 있었다
  (묶기 제안의 주체 PENDING 검사를 컨트롤러만 건너뜀 — 통일 방향은 "주체는 반드시 PENDING").
- **CONFIRMED_BASIC**(물·소금·설탕·간장·식용유·후추·참기름·통깨·다진마늘·고춧가루·식초) = 매칭에서 아예 건너뜀.
  이게 없으면 "완전 가능" 섹션이 구조적으로 항상 0이다. "마늘"은 기본양념이 아니다(떨어질 수 있는 주재료).
  범위는 오너가 사전 화면 `[기본]` 버튼으로 조정(시드는 출발점).
- **기본양념과 그룹 매칭은 보완재** — 하나만 하면 효과가 거의 없다(완전가능 0→2 vs 0→9).
- **[AI 점검]**(온디맨드): 사전 전체를 1회 호출로 보내 분류·병합 후보를 **제안**으로만 적재(자동 적용 없음,
  CONFIRMED 덮어쓰기 없음). 묶기 제안은 **대표 전체**를 보낸다(PENDING 만 보내면 대표 후보가 사라짐).
  호출부가 사전 사실과 대조해 거른다: 지어낸 이름 · 없는 대표 · 체인 · 이미 그 그룹.
  `[제안 전체 적용]` 은 확인창 1번(없는 이름은 404 아니라 조용히 건너뜀). 되돌리기 = 행마다 [그룹 해제] 1탭.
- **AI 가 제안하지 않은 묶기를 오너가 직접 지정하는 UI 는 없다**(백엔드 `/dictionary/merge` 는 이미 받는다).
  필요해지면 검색+대표 선택 UI 를 추가한다.
- `RecommendRules.classify()` 는 DB 사전 조회, `match()` 는 `match_key` 비교.

## 10. 재료 신고 (전력 재분석, 구현 완료)
- 성격: **일반 사용자 기능**. 공개 전이라 노출·API 둘 다 허용 목록(오너)으로 임시 게이트
  (프론트 `RecipesPage canReport` + 서버 `requireOwnerWhileGated`). 공개 시 게이트만 푼다.
- **공개 시 게이트 해제와 함께 필수**: 신고된 재료명이 검증 없이 Gemini 프롬프트에 들어간다(prompt injection).
  해당 영상 `recipe_json` 의 재료 목록에 실재하는 이름만 허용하도록 검증을 반드시 함께 넣는다.
- 처리: 사전 항목 재판정이 아니라 **영상 전체를 신고 힌트와 함께 재분석**(기존 대기열 재사용 — 재시도·
  백오프·모니터링·2인스턴스 안전을 그대로 상속). 힌트는 `video.report_ingredient`(V15),
  힌트가 있으면 로컬을 건너뛰고 **Gemini 직행**. 프롬프트는 "확실하지 않으면 기존 표기 유지"로 할루시네이션 방지.
- 노이즈 제거: **1인 1신고를 DB UNIQUE 가 강제**(`ingredient_report`). 임계값 = 서로 다른 신고자 수
  (`report-analyze-threshold`, 지금 1). (영상·재료)당 재분석 상한(`report-max-runs`, 지금 2) 으로 무한 루프 차단 —
  상한 뒤 신고는 기록만 남는다.
- 관찰: `ingredient_report_run` 에 실행별 전후 재료 diff. new 가 NULL 이면 재분석이 FAILED. 전용 화면 없음 —
  패턴이 보이면 그때 설계.

## 11. 냉장고
- 있다/없다만 관리. 수량·유통기한 입력 없음(입력 부담이 기능 생존의 최대 변수). 등록일 자동 기록,
  같은 재료 재등록 시 등록일을 오늘로 갱신.
- 선반 3칸: 임박(수동 토글) / 오래됨(`OLD_THRESHOLD_DAYS`=14 경과) / 신선. 빈 선반은 숨김.
  각 선반은 스냅 가로 스크롤 + 오른쪽 페이드. 신선만 최신순(새것이 왼쪽), 나머지는 오래된 순.
- 재료 = 자석 스티커. 탭 → 시트에서 임박 토글·이름 수정·삭제(확인 없이 즉시).
- 등록일 변경은 **달력 없이 −1일/+1일 스테퍼**(누를 때마다 즉시 저장, 미래 날짜 불가).
  상대 버튼(오늘/어제/2일 전)은 만들었다가 제거함 — **다시 제안하지 말 것**.
- 추가: 선반 아래 전체폭 [+ 재료 추가] → 시트(자주 사는 재료 12개 토글 + 자유 입력).
  카테고리 트리 탐색은 만들지 않는다. 시트는 연속 추가를 위해 추가 후에도 안 닫는다.
  **이 화면은 세로로 안 늘어나므로 FAB 이 아니라 전체폭 버튼이 맞다 — 바꾸지 말 것.**
- 자주 사는 재료는 **화면 진입 시 1회만 정렬**(조작 중 재정렬하면 버튼이 자리를 옮겨 연타가 불편).
  개수는 `FREQUENT_LIMIT`. [편집]으로 목록에서 제거 가능(냉장고 안 재료엔 영향 없음, 직접 입력하면 해제).
  시드 = 한국 가정 상비 재료 12개.
- 추가 피드백: 시트 상단 "방금 넣음" 확인줄 + 시트를 닫으면 새 스티커가 "아래에서 올라와 쾅" 1회 연출.
  효과는 이 단일 연출만(조합·다중 효과 기각). `prefers-reduced-motion` 이면 생략.
- 추가 시트의 **전환형 한 자리**(입력창 **위**): 빈 입력=구매 추천 / 입력 중=사전 자동완성(동시 표시 금지).
  위에 두는 이유 = 키보드 안전 지대 규칙. 입력창은 자판 자동완성 차단(`autoComplete off`).
- 자동완성은 사전 **대표 이름**만 최대 6개(포함 매칭, 클라이언트 필터). 퍼지 검색은 1단계 제외.
- 구매 추천 "이거 하나만 사면 만들 수 있어요": 내 보관함 레시피 중 주재료가 **정확히 1개** 부족한 것을
  대표 이름으로 묶어 최대 5줄(표시 전용, 양념 부족은 안 셈).

## 12. 보관함
- 탭 이름은 "레시피"가 아니라 **보관함**(요리 외 유틸·기타도 담기므로). 내부 이름(`domain/recipe`,
  DB `gikka`, 경로 `/recipe/recipes`)은 그대로 둔다.
- 한 화면에 등록 대기열 + 완료 목록(요약 배지 필터가 섹션 분리 역할). 카드 제목은 원본 영상 제목보다
  AI 추출 요리명(`recipe.name`) 우선.
- 등록 버튼은 목록 끝이 아니라 **떠 있는 우하단 FAB**(라벨 있는 확장형) — 목록이 길어지면 전체폭 버튼은
  스크롤 바닥으로 밀려 못 찾는다. 냉장고와 반대인 이유는 세로 길이가 무한히 늘어나기 때문.
- 검색 대상: tags + title + recipe.name. **내 registration 만** 검색한다 — gikka 전체 보완 노출은 폐지
  (남의 데이터가 섞이면 내 데이터가 관리되지 않는다는 인상 + 추천 탭과 중복).
- **내 목록에서 지우기**: `DELETE /api/recipe/registrations/{videoId}` — 요청자의 연결만 삭제
  (video·다른 사용자 무관). 확인 팝업 없이 즉시 + 낙관적 업데이트. 아래 REMOVED 와는 다른 기능.
- **영상 삭제(REMOVED, 오너 전용)**: 영상정보(제목·썸네일·url)는 남기고 분석정보만 지운다 — 다른 사용자
  목록에도 "삭제됨"으로 흔적이 보인다. 재분석하면 복구되고, 재등록되면 자동으로 WAITING 으로 되살아난다.
  여러 사용자에게 영향을 주는 되돌릴 수 없는 동작이라 **확인창 1번**.

## 13. 추천
- 3단계: 1) 완전 가능 2) 양념만 부족 3) 재료 부족(부족 적은 순, **개수 상한 없음** — 상한으로 거르면
  화면이 텅 빈다). 섹션당 **내 보관함 10 + 남의 것 10**, 배치는 **내 것 블록 먼저 → 남의 것 블록**.
- 후보 소스 = **gikka 전체 분석 완료 RECIPE**(콜드스타트 대응). 냉장고 매칭은 내 것 기준.
  카드 테두리로 "내 보관함" 구분(카드 안 배지 금지 — 좁은 카드에서 제목 폭을 먹는다).
  남의 레시피는 상세 시트에서 [내 보관함에 담기].
- 3단계 레이아웃은 **항목 유무와 무관하게 항상 표시**(빈 섹션은 전용 안내 문구로 자리 유지).
  전체가 0개일 때만 안내 문구 하나로 대체.
- **세로 스크롤 없이 3단계가 한 화면**(중첩 flex, 카드는 높이에서 비율로 역산 — 단 `height:100%` 명시
  필수, `frontend/AGENTS.md` iOS 함정 참고).
- 정렬 3단: ① 재료 부족 섹션은 부족 개수 오름차순 ② 임박 재료를 쓰는 레시피 우선
  ③ 나머지 동점은 **일일 셔플**(시드=사용자ID+서버 오늘 — 하루 동안 고정, 날이 바뀌면 회전).
  매 요청 랜덤은 기각(방금 본 카드가 사라짐), 노출 이력 로테이션도 기각(기록 테이블 필요).
- 계산은 LLM 없이 재료 태그 집합 비교. **`RecommendRules.java` 한 파일이 추천 알고리즘의 단일 원본**
  (분류·매칭·3단계 판정·정렬 전부). 컨트롤러는 모아서 넘기기만.
- 성능: 전 사용자 공통 입력(후보 파싱 결과 + 사전 3종)만 `RecommendCandidateCache` 가 TTL 60초·인스턴스별
  캐시(stale-while-revalidate). **사용자별 입력과 매칭 결과는 캐시 금지**(조건별로 달라 틀린 답이 된다).
  TTL 은 부하가 아니라 신선도 조절 장치. 후보 조회는 슬림 5컬럼. SQL LIMIT 불가(상위는 매칭 후에만 앎).
  후보가 수십만이 되면 재료 정규화 테이블(DB측 매칭)로 전환 재검토.
- 로딩은 스켈레톤(실제와 같은 치수의 3섹션 틀 + 카드 자리 펄스) — 개수가 아니라 **치수를 흉내 낸다**.
  썸네일 `loading="lazy"`.
- 커버플로우(`RcpCoverflow`): 가운데 확대 1.15 · 옆 0.62 · 투명도 0.55 · 겹침 -60px(목업에서 확정한 값).
  `paint()` 는 프레임당 DOM 읽기 0회 — 실측값은 `setup()` 이 1회만 잰다(layout thrashing 방지).
  카드는 썸네일 + 흰색 반투명 배지(이름 1줄 + 부족 재료 칩 2개+더보기). 드래그 6px 이상이면 탭 무시.
  컨테이너에 `isolation: isolate`(카드 z-index 가 하단 시트를 덮지 않게).
- 카드 탭 → 하단 시트 상세(재료 있음/없음 · 조리시간 · 조리순서 · 원본 링크). 추가 API 호출 없이 한 응답으로.

## 14. 운영자 모드 (`/recipe/monitor`, 오너 전용)
- **오너 전용 강제 동작(강제 재분석·영상 삭제 등)은 전부 여기 한 곳에 모은다** — 일반 화면에 조건부
  버튼으로 흩뿌리지 않는다. (재료 신고의 임시 게이트는 이 규칙과 다른 것 — 일반 기능의 공개 전 게이트다.)
- 접근 통제는 허용 목록 재사용, **백엔드 403 이 실제 경계**(탭 바에 없다는 건 경계가 아니다).
  진입은 홈 계정 시트의 오너 링크(응답의 `canViewMonitor`).
- 두 형제 탭: 대기열(MonitorPage) + 사전(DictionaryPage). 사전을 보는 동안 대기열 폴링은 언마운트로 멈춘다.
- 대기열: 2초 폴링(SSE 아님 — 격리 규율상 배관 복사 비용이 큼, 다중 사용자 단계에서 승격 검토).
  탐색 3종 = 검색(제목·요리명·태그) / 상태 칩 필터(개수는 LIMIT 무관 전체) / 무한 스크롤 100개씩.
  정렬은 최신 등록순 고정. 항목 탭 → 시트(분석 내용 · 원본 보기 · 강제 재분석 · 영상 삭제),
  분석 내용은 탭한 1건만 별도 조회(폴링 목록에 실으면 2초마다 재전송).
- "밀렸나 / 멈췄나 / 한도인가"를 화면에서 구분하기 위한 4가지: 대기열 크기 · 워커 생존 신호
  (`gemini_rate.heartbeat_at` — `last_call_at` 은 백오프로 미래로 밀려 생존 신호로 못 씀) ·
  완료 소요시간(`analysis_seconds`) · 429 이력(`rate_limit_count`·`last_rate_limited_at`).
  추가로 `geminiRetryCount`·`nextRetryAt`(다음 재시도까지 N초 카운트다운)·`lastError`.
- 사전 화면: **행 하나 = 재료 하나**에 현재 확정값(그린 실선)과 AI 제안(노랑 점선)을 함께 표시
  (제안 블록 분리 금지 — 같은 재료가 두 곳에 나오면 "다른 값으로 바꿔 확정"하는 경로가 사라진다).
  확정·제안은 **색과 모양 둘 다**로 구분(색맹 대응). 상태 칩(손볼 것/제안/기본/양념/주재료/묶임/전체) + 검색,
  **검색어가 있으면 칩을 무시하고 전체에서 찾는다**. 접기 방식은 기각.
  **즉시 저장**(일괄 저장·미저장 상태 없음 → 이탈 확인창도 없음). 여러 건을 바꾸는 `[제안 전체 적용]` 에만 확인창.
  멤버 행은 분류 버튼 대신 `→ 대표` 배지 + [그룹 해제]만(멤버에게 분류 버튼을 주면 거짓말이 된다).
- 목록 구성 판정(제안 병합·칩·검색·개수)은 `data/dictionaryFilter.ts` 순수 모듈 + vitest.
- admin/test 영역으로의 이관은 기각 — 다른 인증 체계(useAdminAuth)라 recipe 세션·격리 규율과 안 맞는다.

## 15. AI 점검 동기 호출 — 전용 경로 `/api/recipe/llm/**` (임시)
- `/api` 는 대화형 요청(100ms대, `proxy_read_timeout 15s`)용이라 동기 LLM 호출(10~25초)이 504 로 끊긴다.
  **둘 다에 맞는 타임아웃 값은 없다** → 이 부류만 전용 경로로 분리하고 nginx 에
  `location ^~ /api/recipe/llm/ { proxy_read_timeout 120s; proxy_next_upstream off; }`.
- 경로 이름이 권한(`admin`)이 아니라 `llm` 인 이유: nginx 규칙이 의존하는 성질은 "오너 전용"이 아니라
  **"오래 걸림"** 이다. `proxy_next_upstream off` 가 없으면 타임아웃마다 app-2 에 같은 호출이 한 번 더 가
  무료 한도를 두 배로 태운다.
- 함께: `thinkingConfig.thinkingBudget=0`(24.7→10.9초, 폐쇄적 어휘 판단이라 품질 동등) ·
  `TransientFailureException`→503 · `[점검 중…]` 표시.
- **승격 조건**: 느린 오너 기능이 하나 더 생기거나 사전이 커져 다시 15초에 근접하면 → 대기열·워커·폴링으로
  비동기화하고 이 경로와 nginx 블록을 **삭제**한다.
- **주의**: nginx 설정은 저장소 밖이다. 바꾸면 mac-mini 실물과 `chs/server/nginx/devcontext.conf` 백업
  **둘 다** 고칠 것. `/chs/` 는 .gitignore 라 다른 PC 는 백업을 못 본다 — **실질적 단일 원본은 서버 실물**.

## 16. 확장성 선반영 (데이터 모양만 — 1단계 UI 에는 노출 안 함)
- `platform`: 영상 출처(1단계 항상 YOUTUBE, 향후 TIKTOK·REELS).
- `category`: RECIPE/TIP/ETC 를 분석이 판정·저장(2단계에서 TRAVEL·EXERCISE·DIY·STUDY 등으로 세분화).
- `summaryVersion`: 추출 모델·프롬프트 세대. 올리면 구버전 요약만 골라 재생성 가능.
- 개인 목록 커스터마이징(폴더칩 등)은 스키마에 선반영하지 않는다 — 모양이 안 정해졌고, 카테고리 오분류는
  재분석 + 품질 개선으로 대응하는 게 우선. `registration` 은 최소 스키마 유지.

## 17. 사후 비공개 감지 (설계 확정 — 미구현, 이 절이 단일 원본)
- 공개일 때 분석된 영상이 나중에 비공개·삭제되는 것을 잡는다. RECIPE 는 원본이 사라져도 추출 결과가
  남아 가치가 유지되므로 급하지 않다.
- 방식: 하루 1회 스케줄러가 **50개씩 묶어** `videos.list` 호출 → 응답에서 빠진 영상 = `source_unavailable`
  ON, 있으면 OFF(다시 공개되면 자동 복구). 2인스턴스 단일 실행은 워커의 SKIP LOCKED 재사용.
- **REMOVED 를 재사용하지 말 것(핵심 안전 규칙)**: REMOVED 는 분석 결과를 함께 지워, 그 영상을 등록한
  **전 사용자의 재료·조리법이 한꺼번에 조용히 소실**된다. 자동 감지는 반드시 별도 플래그를 쓴다.
  (분석이 사라지는 유일한 경로는 오너의 명시적 강제 재분석·영상 삭제뿐이다.)
- 비용: `videos.list` 는 50개/1유닛 — 고유 영상 1만 개 전체 훑기 = 200유닛(하루 한도의 2%).
- **유튜브 유닛 계기판(함께 구현)**: YouTube Data API 는 남은 유닛을 응답으로 안 준다 → 직접 센다
  (`youtube_quota` 테이블, 호출마다 원자적 +1, 태평양 자정 리셋). 모니터 화면에 "오늘 소모 N / 10,000".

## 18. 2단계 착수 준비 — 앱 분리
- 셸: **TWA**(Bubblewrap) 채택 — 지금 PWA 를 그대로 감싸며 실제 도메인을 여는 방식이라 오리진이 같다.
  위치 기반 알림(geofencing)이 필요해지면 **Capacitor 로 교체** 예정.
  **안드로이드 패키지명(applicationId)은 최초 설정 그대로 유지해야** 스토어 실적·설치 이력이 안 끊긴다.
- 교체 비용: 화면·스타일·도메인 로직은 재사용되지만 **구글 로그인은 재작업이 불가피**하다(웹 GIS 는
  WebView 에서 정책상 차단, TWA 는 속이 진짜 크롬이라 통과). 범위는 `data/googleSignIn.ts` 하나로 묶어 뒀다.
  함께 딸려오는 것: 오리진이 `https://localhost`·`capacitor://localhost` 가 되므로
  `gikka.auth.allowed-origins` 를 채워야 하고(비 http 스킴은 `allowedOriginPatterns` 사용),
  저장소가 바뀌어 **전 사용자가 한 번 로그아웃**된다(교체 배포 시 안내 필요).
- 도메인: `gikka.devcontext.net`(전용 도메인 구입 보류).
- 프론트 격리(미구현): 호스트네임이 `gikka.devcontext.net` 이면 `RecipeApp` 만 루트에 마운트하고 다른
  라우트는 등록조차 안 한다. 완전 별도 빌드 파이프라인은 안 만든다(코드 분할이 이미 있음).
- 백엔드 분리(미구현): 배포가 서로 영향을 주면 안 되므로 **완전히 별도 Spring Boot 서비스**로 분리
  (별도 이미지·`chs-gikka-1,2`·별도 Jenkins stage). 새 프로젝트는 저장소 루트 `gikka/`.
- **되돌릴 수 없는 스토어 결정**: applicationId `net.devcontext.gikka`(셸 기술 이름을 넣지 말 것) /
  **Play App Signing 사용**(업로드 키 분실 시 재발급 가능) / `assetlinks.json` 의 SHA-256 은 업로드 키가
  아니라 **Play Console 이 발급한 앱 서명 키** 지문(틀리면 앱이 죽지 않고 주소창 보이는 브라우저 모드로 조용히 떨어진다).
- **네이티브 전환 대비의 판단 기준**: **지금 한다 = 나중에 하면 여러 파일로 번지는 것 /
  나중에 한다 = 그때도 파일 하나만 갈아끼우면 되는 것.**
  이미 처리 — `tokenStorage.getToken()` 동기 고정 + `initTokenStorage()` + 셸 `storageReady` 게이트 /
  `data/platform.ts`(환경 API 집결) / `data/googleSignIn.ts`(GIS 격리) / `platformIsolation.test.ts`(가드).
  미룬 것 — Share Target 진입점, `'/recipe'` 경로 하드코딩, X다운로드 blob 저장, 안드로이드 하드웨어 뒤로가기.
- 남은 수동 작업(코드 아님): DNS · nginx 서브도메인 · OAuth 승인 오리진 추가 · Play Console 비공개 테스트 ·
  키스토어 백업. (진행 상황은 `docs/HANDOFF.md`)

## 19. 격리 규율 (ArchUnit 이 강제)
1. 코드: 백엔드는 `domain/recipe` 안에서만, 다른 도메인과 상호 참조 금지. 프론트는 `src/domain/recipe/`.
2. DB: recipe 전용 데이터베이스 + 전용 DataSource. 기존 테이블과 외래키·조인 금지.
3. API: `/api/recipe/**` 통일.
4. AI 호출: 인터페이스 뒤에 숨김(구현체 교체로 끝나게).
5. 설정: recipe 관련 설정은 별도 설정 그룹(`gikka.*`).
6. 격리 자동 감시: ArchUnit 테스트가 빌드에서 차단 — 규율을 사람 기억이 아니라 테스트가 지킨다.
7. **공용 코드 허용 목록: 없음.** 기존 home 유틸이 필요하면 recipe 안으로 복사해 소유한다(앱 분리 대비).
8. recipe 쪽 TransactionManager 스프링 빈 등록 금지 — `gikkaTxTemplate` 로만.
9. **recipe 안쪽 방향 규칙(2026-07-25)**: `dictionary` 는 `registration` 을 import 하지 않는다
   (ArchUnit 이 강제). 사전은 registration 의 산출물이자 recommend 의 입력이라 어느 한쪽 소유가
   아니어서 별도 패키지로 뒀는데, 양방향이 되면 패키지 순환이라 분리한 이득이 사라진다.
   이 규칙 때문에 **LLM 판정 6개(`IngredientJudge`·`DictionaryJudge`·어댑터 등)는 registration 에
   남겼다** — `GeminiJsonClient`·`GikkaMediaProperties`·`TransientFailureException`·
   `LocalUnavailableException` 을 쓰기 때문. 그 넷을 중립 지대로 옮기기 전에는 판정도 못 옮긴다.
10. **컨트롤러는 청중 단위로 나눈다(2026-07-25)**: 보관함 `RegistrationController` / 운영자 대기열
   `MonitorController` / 사전 `dictionary.DictionaryController` / 동기 LLM `IngredientAuditController`.
   경로는 넷 다 **분할 전 그대로**이고 `RecipeRoutingTest` 가 18개 경로를 잠근다(프론트 무수정의 근거).
   사전 경로 `/registrations/dictionary/**` 는 유산 — `gikka/` 분리 때 `/api/recipe/dictionary/**` 로 옮긴다.
11. **오너 판정은 `GikkaOwnerGuard` 하나** — `require`(403으로 막기) / `isOwner`(상한 면제 같은 분기).
   예외: `IngredientReportController.requireOwnerWhileGated` 는 같은 판정을 쓰되 이름을 따로 둔다 —
   그건 오너 전용 기능이 아니라 **일반 기능의 공개 전 게이트**라, 공개 시 지울 호출을 구분해야 한다(10절).

## 20. 구현 순서
1차 디자인·골격·냉장고(완료) → 2차 백엔드 기반(완료) → 3차 Gemini 추출·등록·Share Target(완료) →
4차 보관함·추천(완료) → 5차 품질 향상 + 다중 사용자 준비(진행) → 6차 릴스·틱톡 확장.
- 6차 착수 조건 = 유튜브 추출 품질 합격뿐. 방식: yt-dlp 다운로드 → 기존 추출 프롬프트 재사용
  (platform 필드 선반영 덕에 스키마·화면 변경 없음).
- 인스타 쿠키 운영(무인 목표, 유료 서비스 안 씀): mac-mini 크롬 전용 프로필 로그인 유지 +
  `yt-dlp --cookies-from-browser chrome`. 세션 유지는 launchd 주 1회 페이지 터치. 유효성 체크는
  사용 직전 + 일 1회(매분 체크 금지 — 봇 신호가 되어 쿠키 수명을 줄인다). 실패 시 텔레그램 알림.
  **로그인 자동화·브라우저 조종(Playwright 등) 금지** — 봇 탐지 표적, 계정 정지 위험.
- 품질 합격 기준: 오너 재생목록의 요리 쇼츠 10개를 원본 대조 채점, **10개 중 8개 이상 "재료가 장보기에
  쓸 수 있는 수준"**. 불합격 시 프롬프트 → 해상도 → 유료 소액 순으로 재논의.
