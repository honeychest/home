## 1. 비전과 단계
- 문제: 쇼츠(요리·생활팁)를 재생목록에 저장해두고 필요한 순간에 꺼내지 못한다.
  출발점이 된 말 = "기억해놨다가 필요할때 까먹어야지" — 브랜드 '기까'의 유래(오리지널 문장).
  태그라인(로그인 화면·PWA 설명)은 이 원문을 기반으로 하되, 사용자가 승인한 변형은 허용
  (2026-07-12 확정 — 기존 "변형 금지"는 맘에 안 드는 변형이 쓰였던 것에 대한 규칙이었음.
  현재 로그인 화면 문구 『"기억해놨다가 필요할때 까먹어야지"는 그만, 기까가 꺼내드려요』는 승인됨).
- 장기 비전: 저장한 쇼츠를 필요한 순간에 꺼내주는 앱.
- 1단계(현재): 요리 영역부터. 요리는 "뭐 해먹지"라는 매일 반복되는 트리거와
  냉장고 재고라는 검색 조건이 있어 '꺼내기'가 실제로 작동하는 첫 영역이다.
- 2단계(실사용 검증 후): Android 앱 전환 + 영역 확장 + 중앙 분석 DB 공유
  (영상 ID당 분석 1회, 사용자 개인 DB는 영상 ID + 개인 데이터만 보유).
- 상용화 기획(브랜드 네이밍 '기까/Gikka' 후보, 광고 BM, 계정 동기화 등)은
  아이디어만 존재하는 상태. 2단계 착수 시 별도 문서로 정리한다. 1단계에서는 만들지 않되,
  아래 "확장성 선반영" 절의 데이터 모양만 미리 대비한다.
- 틱톡/릴스 확장은 아이디어가 아니라 확정 기능 (2026-07-11 사용자 확정 — "무조건 한다,
  순서 문제일 뿐"). 유튜브 추출 품질 검증 후 6차로 구현한다 (구현 순서 참고).

## 2. 확정 설계 결정 (2026-07-08 인터뷰)

### 플랫폼·저장
- 형태: 모바일 웹앱. S25 홈화면에 추가해 앱처럼 사용. mac-mini의 home 서비스에서 제공.
- 위치: home 프로젝트에 recipe 도메인으로 추가 (nexus에 넣지 않음 — nexus 비대화 방지).
- DB (2026-07-10 구체화): 이미 가동 중인 PostgreSQL 컨테이너(chs-pgvector, 챗봇 벡터용)에
  `gikka` 데이터베이스를 신설한다. 컨테이너 추가 없음. 전용 계정 `gikka`는 gikka DB만
  접근 가능하게 하여 챗봇 데이터(chs_vector)와 상호 접근을 차단. 기존 DB와 완전 분리.
  (2차 백엔드 단계부터. 이름은 브랜드 '기까'를 따름 — recipe_db 아님)

### 개발 방식 (프론트 우선)
- 프론트를 먼저 완성한다: 백엔드 없이 화면만 만들어 오너가 폰에서 직접 조작하며
  반복 수정하고, "완전해졌다"고 판단한 뒤에 백엔드를 하나씩 연결한다.
- 프론트 단독 기간의 저장은 localStorage. 단, 화면이 저장소를 직접 부르지 않고
  저장소 인터페이스(repository)를 거치며, 데이터 모양은 미래 API 응답과 동일하게 설계한다.
  → 백엔드 연결 = localStorage 구현체를 API 구현체로 교체하는 것으로 끝나야 한다.
- 디자인은 모바일 전용만 만든다 (최종 목표가 앱이므로 데스크톱 대응 불필요).
- 레시피 데이터가 필요한 화면(추천 등)은 손으로 넣은 샘플 레시피로 개발한다.
- (2026-07-10) 냉장고 UI 확인 완료로 프론트 단독 기간 종료 — 백엔드 단계로 전환됨 (아래 구현 순서).
- 프론트 단독(localStorage) 기간은 최소화한다. UI가 확인되면 즉시 백엔드로 넘어간다.
  localStorage 단계가 길어지는 것 자체를 실패 신호로 간주하며, 유실 대비 백업 기능도
  만들지 않는다 (냉장고 데이터는 유실돼도 재입력 가능한 수준). 브라우저는 크롬으로 통일.

### 디자인 체계 (세션이 바뀌어도 단편적 코딩이 나오지 않기 위한 구조)
- 디자인은 recipe 앱만의 새 디자인이다. 기존 home 디자인과 맞출 필요 없음.
- 디자인 방향 (2026-07-09 인터뷰 확정): "냉장고 문 × 프레시".
  - 라이트 기본: 아이스 화이트(살짝 그린 기운) 배경 + 그린(#1f7a3d 계열) 포인트.
  - 메타포: 재료 토글 버튼은 냉장고 자석 스티커(각진 모서리·그림자·ON은 그린 테두리,
    OFF는 점선 회색), 임박 표시는 포스트잇 노랑. 유치해지지 않게 절제해서 실행.
  - 다크 모드: 시스템 설정 자동 전환. "밤의 냉장고" — 어두운 배경에 같은 그린 포인트,
    스티커 메타포 유지.
  - 시안 아티팩트: https://claude.ai/code/artifact/03664dc1-a3d4-41d7-93d6-11f4b1788d15 (마안)
- 폰 접속 경로: 개발 중에는 같은 와이파이에서 PC vite dev 서버 접속,
  1차 완료 시점에 mac-mini home 서비스에 배포해 홈화면 추가(크롬).
- 기술 스택은 기존 frontend(React 19 + Tailwind 4 + shadcn/ui + lucide 아이콘)를 그대로 사용한다.
- recipe 전용 구조:
  - `frontend/src/domain/recipe/style/tokens.css` — 색·간격·글자 크기·모서리 등을
    CSS 변수로 정의한 테마 세트 (라이트/다크 포함). 디자인의 유일한 원본.
  - `frontend/src/domain/recipe/ui/` — recipe UI 킷. shadcn 기반으로 조합한
    공용 컴포넌트(버튼, 목록 행, 카드, 배지, 하단 시트 등)만 여기에 둔다.
  - `frontend/src/domain/recipe/page/` — 화면. 반드시 tokens.css 변수와 ui/ 킷만
    사용해 조립한다. 화면 코드에 임의 색상값·임의 크기 직접 입력 금지.
  - `/recipe/styleguide` 페이지 — 토큰과 ui/ 컴포넌트 전부를 한 화면에 나열.
    새 세션의 AI는 화면을 만들기 전 이 페이지(코드)를 참조하고,
    새 공용 컴포넌트를 만들면 반드시 여기에 등록한다.
- 규칙: 새 화면에서 스타일이 아쉬우면 화면에서 고치지 말고 tokens.css 또는 ui/ 킷을
  고친다 (전 화면에 일괄 반영되도록). 1차 시작 시 tokens.css와 기본 킷부터 만든다.
- 다국어 대비 규칙 (2026-07-09 검수에서 확정, 2026-07-14 갱신): 모든 UI는 글자 길이가
  2~3배로 늘어도 깨지지 않아야 한다. 킷 공통 — 버튼·칩은 줄바꿈 금지+짓눌림 금지(내용만큼
  넓어짐), 탭은 말줄임. 목록 행의 이름류(제목 등)는 무제한 줄바꿈 대신 최대 2줄 + 말줄임
  (line-clamp) — 카드 레이아웃 안정성(2026-07-14 확정, RcpVideoRow 사례. 무제한 줄바꿈이
  카드 높이를 들쭉날쭉하게 만드는 문제가 실사용에서 발견돼 대체함. 전체 내용은 상세
  화면/시트에서 확인 가능해 정보 손실 없음). 배지 등 우측 상태값 영역도 라벨 길이가
  제각각이면 고정 최소폭을 줘 좌측 영역 폭이 행마다 흔들리지 않게 한다. 그 외 영역은
  고정 너비 금지, min-height만 사용. /recipe/styleguide의 "긴 글자 스트레스 테스트" 절이
  검증 장치 — 새 공용 컴포넌트를 만들면 반드시 여기에 긴 문자열 케이스를 추가한다.
- 언어 계획: 한국어 기본. 영어는 고도화(2단계) 때 i18n 도입으로 추가.
  1단계에서는 레이아웃 내성(위 규칙)과 문구/데이터 분리(PLAYBOOK 품질 기본선)만 지킨다.
- 배지 색 체계 (2026-07-14 확정, dataviz 스킬로 CVD 검증): "채움=정상/테두리=문제" 구분을
  폐지하고 전부 같은 파스텔 칩 모양으로 통일 — 의미는 오직 색으로 구분한다. 두 팔레트가
  절대 안 겹치게 분리: (1) 카테고리(콘텐츠 분류) — cat-1~8 고정 순서 팔레트(tokens.css).
  1~3 사용 중(레시피=파랑·유틸=청록·기타=노랑), 4~8은 2단계 확장 예비(여행/운동/DIY/공부
  등 — 새 카테고리는 반드시 이 순서 그대로 다음 슬롯을 쓴다, 순서 변경 금지가 색맹 구분성의
  근거). (2) 상태(진행 상태) — neutral/analyzing/good/warning/serious/critical 예약색,
  카테고리 팔레트와 절대 혼용 금지. 색 선정은 dataviz 스킬 `validate_palette.js`로 색맹
  구분성(CVD)·명도·채도를 실측 검증(눈대중 금지) — 새 카테고리·상태를 추가할 때도 같은
  방식으로 검증할 것.
- 하단 시트 패턴 (2026-07-14 확정, RcpBottomSheet 킷 컴포넌트): 최대 70% 높이로 열려 위
  30%는 항상 배경(overlay) 노출(탭으로 닫기), 헤더(핸들+제목)를 아래로 쓸어내리면 닫힘
  (60px 임계값) — 콘텐츠가 화면을 꽉 채워도 항상 닫을 수 있는 영역 확보. X 버튼 대신 이
  방식을 선택. `.rcp-sheet`에 `overscroll-behavior-y: contain`도 적용(시트 내부 스크롤이
  맨 위에서 브라우저 pull-to-refresh 로 새는 것 방지).

### 앱 골격과 홈 화면 (2026-07-09 점검에서 확정)
- 하단 탭 4개: 홈 / 추천 / 냉장고 / 레시피. 1차에서는 냉장고만 동작하고 나머지는 자리만 둔다.
  등록(URL 일괄)은 별도 탭이 아니라 레시피 탭 안의 버튼.
- 홈 화면의 최종 UX: 링크를 복사한 채 앱을 열면 바로 분석이 시작된다.
  - 웹 단계: 브라우저 보안상 클립보드 자동 읽기가 불가하므로 "붙여넣기" 버튼 1탭으로 구현.
  - 붙여넣기 = 즉시 분석 (2026-07-16 확정, 보관함 등록 시트): 붙여넣기 버튼뿐 아니라 입력창에
    직접 붙여넣어도(`onPaste`) 바로 분석이 시작된다 — [등록] 버튼을 또 누르지 않는다.
    계기: 클립보드 읽기 API 가 없는 http 개발 서버(폰 LAN 접속)에서는 붙여넣기 버튼이 통째로
    숨겨져 "길게 눌러 붙여넣기 → 등록 탭" 2단계가 되던 것을 사용자가 지적. paste 이벤트는
    앱이 클립보드를 몰래 읽는 게 아니라 사용자가 붙여넣은 것을 브라우저가 알려주는 것이라
    비보안 컨텍스트에서도 동작한다 — 그래서 "버튼이 없으면 미리 채워두기"는 여전히 구현
    불가지만(읽기 자체가 막힘) "자동 분석"은 가능하다. [등록] 버튼은 유지(직접 타이핑·부분
    수정 경로). 홈 탭의 개발 모드 안내는 그대로 둠 (2026-07-16 사용자 결정 — 개발 모드
    한정 불편이고, 배포[https]에서는 붙여넣기 버튼이 정상이며 메인 동선은 Share Target 이라
    배포 화면에 쓸모없는 입력창을 더할 이유가 없음).
  - PWA Share Target 확정 (2026-07-11 사용자 확정 — 후보에서 승격): 유튜브·인스타·틱톡 앱의
    공유 메뉴에서 기까를 선택하면 바로 분석이 시작된다. "나에게 보내기"를 대체하는 핵심 동선.
    3차(등록 화면)에서 구현. 공유 시트 상단 노출은 앱이 강제할 수 없으므로
    오너가 설치 후 공유 시트에서 기까를 길게 눌러 고정(pin)하는 것으로 해결.
  - 2단계(네이티브 앱): 앱 실행 시 클립보드 자동 감지로 승격.
- 홈에는 최근 분석된 쇼츠 섬네일 목록을 표시한다 (레시피 데이터가 생기는 2~3차에서 구현).
- 앱 표시명은 '기까'. 최소 PWA manifest(이름·아이콘·전체화면)를 1차에 포함해
  홈화면 추가 시 앱처럼 뜨게 한다.

### 인증 (2026-07-10 확정)

### 로컬 모델 페일오버 (2026-07-14 구현 완료 — 실측 검증됨)
- 계기: 재시도 로직(위 "일시적 실패" 절) 실사용 검증 중 Gemini 무료 등급이 미국 낮 시간대에

- 실측 검증(2026-07-14, 실제 등록 영상 vs 기존 Gemini 결과 대조): 로컬(프레임+STT+설명란)이

### Gemini 검증 실패 시 즉시 로컬 결과 채택 + 모니터링 가시성 (2026-07-14 확정·구현 완료)
- 계기: "피씨방 라면 100% 똑같이 먹는법" 영상이 ANALYZING 에서 2분 넘게 안 끝나는 걸 사용자가
  발견. 조사 결과 로컬이 TIP/ETC 로 분류해 Gemini 재검증을 타는 경로에서, Gemini 가 429·503 을
  반복해도(대기 시각 mac-mini DB 실측: `gemini_rate.rate_limit_count=392`, 이 영상은
  `last_rate_limited_at` 로부터 정확히 60초 뒤 `analyzing_started_at` 이 재기록돼 재시도임을
  확인) 화면엔 아무 정보 없이 시간만 흐르고, 로컬로 되돌아가는 안전장치가 아예 없어 무한
  반복될 수 있는 사각지대였음(대화로 원인 규명 후 확정).

  `TARGET_FRAMES` 만 바꿔가며 같은 파이프라인을 직접 호출. **전사 글자 수가 양쪽 동일**해서
  (음성 고정, 프레임만 변수) 통제된 비교가 된다. 앞으로 로컬 품질 실험은 이 방식을 쓸 것.
- 실측 5건 결과: 실패 2건(37·53초)이 **24장에서 둘 다 떡 잡힘**. 56초 영상은 6개→10개.
  11초·341초는 동일(회귀 0건). 비용은 341초에서 44→56초(27%), 56초에서 10→19초.
- 덤으로 확인된 것: 24장에서 표기가 정확해지고(설탕→황설탕, 어묵→사각어묵) **없는 재료를
  지어내던 환각("후추장")이 사라졌다** — 화면을 덜 본 모델이 빈칸을 상상으로 메우고 있었다는
  해석과 맞는다. 또 12장은 같은 영상에서 11개→6개로 흔들렸는데 24장은 10개를 안정적으로
  건졌다 — **프레임을 늘리면 비결정성 자체가 줄어든다.**
- 짧은 영상은 영향 없음: 간격 하한(`MIN_FRAME_INTERVAL_SECONDS`=2) 때문에 약 25초 미만은
  `TARGET_FRAMES` 를 올려도 프레임 수가 그대로다. 실패 사례가 전부 37초 이상이었던 것과 일치.
- 더 올리는 것(36장 등)은 시험 안 함 — 24로 알려진 실패가 전부 해결돼 실익이 불확실하고
  시간만 든다. 품질 문제가 또 나오면 그때 같은 방법으로 검증할 것.

### 영상 분석의 테이블 분리 (2026-07-13 확정·구현 완료 — improve-codebase-architecture 점검에서 실행)
- registration 한 테이블(사용자별 분석 저장)을 video(분석 원본, video_id 당 1행) +
  registration(사용자 연결: user_id·video_id·등록일)으로 분리했다.

  영상 ID당 분석 1회가 구조로 보장 (2단계 중앙 DB 공유의 로컬 선행 형태).
- 동작: 등록 시 video 에 이미 있으면 메타 조회 없이 연결만 추가. 대기열·워커·요청속도 제어는
  전부 video 기준(VideoRepository). 재분석은 영상 단위(등록한 모든 계정에 반영 — 재분석
  권한 제한은 2단계에서).
- `video.queued_at` 신설 — 대기열 순번(FIFO) 기준. 이전엔 registration.registered_at 이
  이 역할을 겸했으나 대기열이 영상 단위로 도니 분리(최초 등록 시각으로 시작, 재분석 시
  now() 로 갱신되어 맨 뒤로). registration.registered_at 은 이제 "내가 언제 등록했나"
  (개인 목록 정렬용)만 담당.
- API 응답 모양은 유지(RegistrationController 가 registration·video 조인) — 프론트 무수정 확인됨.
- 저장소도 책임별로 분리: VideoRepository(영상 CRUD·대기열·요청속도 제어·모니터링 카운트/워커상태) /
  RegistrationRepository(사용자 연결 CRUD·화면용 조인 조회·모니터링 목록).
- 실제 마이그레이션은 V7 (문서 최초 작성 시 "V5" 로 적었던 건 그 사이 V5·V6 이 모니터링
  컬럼으로 먼저 나가며 번호가 밀린 것 — 실행 시점 실제 번호로 정정).
- 개인 목록 커스터마이징(폴더칩·카테고리 재분류 등) 방향은 고려하되 지금은 스키마에
  선반영하지 않음(2026-07-13 판단) — 모양(폴더 1개/다중/계층 등)이 아직 안 정해졌고,

  우선이라는 결론. registration 은 지금은 최소 스키마(user_id, video_id, registered_at) 유지.

### 재료·양념 분류 (2026-07-14 4차 grill-me 확정 + 실사용 채점으로 보정 — 추천 계산의 기반)
- 재료 정규화(대파=파 통합 등)는 원칙적으로 하지 않는다 — 원문 그대로 정확 매칭.
  단, 실제 등록된 레시피("캔참치" 채점)로 명백한 **표기 차이**가 발견되어 좁게만 예외
  처리한다(2026-07-14 확정): "다진 마늘"(띄어쓰기)="다진마늘", "백식초"="식초" — 사용자가
  "이건 같은 거다"라고 직접 확인한 것만 별칭(ALIASES) 처리. 반대로 "맛소금"≠"소금",
  "진간장"·"양조간장"≠"간장"은 실제로 다른 재료라는 사용자 판단으로 합치지 않음 — "정규화
  기준이 애매하다"던 지점이 이 실사례로 정리됨: 표기 차이면 흡수, 종류가 다르면 안 흡수.
  추가 사례가 쌓이면 같은 기준으로 ALIASES 에 늘려간다.
- 재료를 MAIN(재료) / SEASONING(양념) 2단계로만 분류(3단계로 세분화할 수 있게 확장 여지를
  남긴 순수 판정 함수). 양념은 매칭(냉장고에 있어야 추천됨)에서 전부 제외하되, 부족분은
  상세·추천 카드에 표시는 한다(구매 유도는 5차 이후 점진 확장 — 쿠팡 등 연동 아이디어는
  사용자 언급, 상용화 기획 문서로 이월).
  목록·별칭은 전부 백엔드 `RecommendRules.java` 한 파일의 코드 상수(관리 화면 없음 — 지금
  규모[오너 1인, 항목 소수]에서는 화면보다 코드 배포가 더 가볍다는 판단, 나중에 자주 바뀌어
  귀찮아지면 DB+오너 화면으로 승격 검토). 이 파일 하나가 추천 알고리즘 전체의 단일 원본
  (2026-07-14 사용자 요청 — "알고리즘 관련 로직은 파일 하나에 정리돼야 나중에 수정할 곳을
  파악하기 쉽다". 재료/양념 분류·매칭·3단계 판정·정렬이 전부 여기 있음).
  양념 목록: 물, 소금, 설탕, 간장, 고추장, 고춧가루, 된장, 후추, 식용유, 참기름, 들기름,
  다진마늘, 다진생강, 맛술, 식초, 물엿, 올리고당, 전분가루, 통깨 (19개).
- "밥"(쌀밥)은 지금은 그냥 재료(MAIN)로 둔다(2026-07-14 확정 — "물보단 재료 느낌이지만
  한국에선 구분이 별로 필요없다"는 의견은 있었으나 보류, 나중에 재검토).
- 상세 화면(보관함 탭)에 재료별 냉장고 보유 여부(있음/없음)를 표시 — `.rcp-chip-on`/
  `.rcp-chip-off`(기존 냉장고 토글과 같은 시각 언어) 재사용, 새 스타일 안 만듦.

### 추천 (2026-07-14 4차 구현 + 실사용 발견으로 즉시 보정)
- 3단계 구조(2층→3단계로 변경, 실사용 시나리오 논의로 확정):
  1) 완전 가능(재료·양념 다 있음) 2) 양념만 부족(재료는 다 있음) 3) 재료 부족(부족 적은
  순 정렬, **개수 상한 없음**) — 각 섹션 최대 5개까지만 화면에 보여줌.
  ("4개 이상 부족은 제외" 초안은 실사용 첫 테스트에서 바로 뒤집힘 — 등록한 레시피 대부분이
  4개 넘게 부족한 상황에서 상한으로 걸러버리니 추천 화면 전체가 텅 비어 기능 자체가
  무의미해짐. "몇 개가 부족하든 부족한 순서대로는 항상 보여줘야 한다"로 정정, 2026-07-14).
- 3단계 레이아웃은 항목 유무와 무관하게 **항상 표시**한다(2026-07-14 확정 — 일부 섹션만
  0개일 때 레이아웃이 들쭉날쭉 사라지는 걸 사용자가 지적. 빈 섹션은 그 섹션 전용 안내
  문구로 채워 자리를 지킴. 등록된 요리가 아예 0개일 때만 예외로 전체 안내 문구 하나로 대체).
- 레이아웃은 **폰 화면 높이에 맞춰 세로 스크롤 없이** 3단계가 항상 한 화면에 들어간다
  (2026-07-14 확정 — 중첩 flex 로 3섹션이 남은 높이를 균등하게 나눠 가지고, 커버플로우
  카드도 고정 px 대신 그 높이에서 비율(aspect-ratio)로 역산돼 자동으로 커지고 작아짐).
- 정렬: 재료 부족 섹션만 부족 개수 오름차순. 임박 재료 가중치는 이번 구현에 넣지 않음
  (나중에 필요성이 확인되면 `RecommendRules.java` 의 정렬 Comparator 만 바꾸면 됨 — 파일
  안에 확장 지점 주석으로 남겨둠).
- 계산: 재료 태그 집합 비교, LLM 사용 안 함(비용 0, 즉시 응답) — `RecommendRules`(순수,
  알고리즘 단일 원본)가 담당, `RecommendController`(`GET /api/recipe/recommend`)가 냉장고·
  완료 레시피를 모아 넘김.
- 레이아웃은 겹침형 커버플로우(coverflow) — 가운데 카드 확대(1.15배)되며 옆 카드와 겹치고
  (겹침 -60px), 옆 카드는 축소(0.62배)·반투명(0.55). 클로드 아티팩트 목업으로 사용자가
  슬라이더를 직접 조작해 확정한 값 그대로 `RcpCoverflow` 상수화(styleguide 등록 완료).
  카드는 썸네일 + 흰색 반투명 배지(이름 1줄+말줄임 상단, 부족 재료/양념 칩 하단 최대
  2개+더보기) — 검은 배경 그라디언트+흰 글자 방식은 "게임 아이콘 같다"는 피드백으로
  기각, 사진 밝기와 무관하게 항상 대비가 보장되는 불투명 배지로 대체.
- 카드를 탭하면 하단 시트로 상세(재료 있음/없음 체크 · 조리시간 · 조리 순서 요약 · 원본
  영상 링크)를 보여준다(2026-07-14 확정 — 보관함 탭 결과 시트와 같은 시각 언어
  `.rcp-chip-on`/`off` 재사용). 백엔드 `RecommendItem` 에 `ingredients`(원문 순서+있음/없음)·
  `cookMinutes`·`steps` 를 실어 보내 추가 API 호출 없이 카드·팝업을 한 응답으로 그린다.
  스와이프 끝에 손을 뗄 때 의도치 않게 팝업이 열리는 걸 막기 위해 드래그 중 6px 이상
  움직였으면 탭을 무시한다(`RcpCoverflow.onCardClick`).
- 실사용 중 CSS 버그 2건 발견·수정(원인·해결은 PLAYBOOK.md "함정 — CSS" 절에 재발 방지
  메모로 남김): ① 세로 스크롤 없이 화면 높이에 맞추는 중첩 flex 구조에서 페이지 루트에

  로컬 라우팅 구조(HybridRecipeExtractor) 자체는 안 바꾸고, 아래 1번 프롬프트 안전화로 대응.
- 우선순위: 1(프롬프트 안전화) → 2·3(검색·추천 확장, 같은 데이터 소스 변경이라 함께 진행)
  → 4(재료 사전+판정 큐, 가장 크고 다중 사용자 착수와 무관하니 마지막).
  콘텐츠 오류 "신고" 버튼 + 오너 수정 화면은 이번 범위에서 제외(2026-07-14 사용자 결정 —
  "지금 할 일은 아닌 듯", 필요성이 쌓이면 재검토).

1. **ETC/TIP 프롬프트 안전화** (2026-07-14 구현 완료로 정정 — 별도 작업 중 코드 확인):
   요약의 서술 정확도보다 검색용 키워드/태그가 더 중요하다는 사용자 판단(앱의 핵심 가치는
   "가물가물한 기억에서 찾아 원본 영상을 보여주는 것"이지 정확한 재서술이 아님) — 프롬프트에
   "화면·음성에서 확인되지 않는 고유명사(선수명·지명·특정 사실 등)는 단정하지 말고, 확인되는
   범위(텍스트 오버레이·자막 등)만 서술하라"는 지시를 추가한다. RECIPE 재료 추출 프롬프트는
   건드리지 않음(이미 원문 저장 원칙으로 안전, 이번 문제는 TIP/ETC 요약에 한정).
   → `GeminiRecipeExtractor` 프롬프트에 이미 반영돼 있음을 확인(`b8eaea9`에서 함께 들어감,
   progress.html 의 "다음 세션부터"가 낡은 기록이었음). 위 "Gemini 검증 실패 시 즉시 로컬
   결과 채택" 절 참고.
2. **보관함 검색 + gikka 전체 보완** (기존에 별개로 논의되던 "보관함 검색"과 "콜드스타트
   전체 영상 노출"이 그릴미 중 하나로 합쳐짐): 보관함(RecipesPage) 자체는 지금처럼
   본인 registration만 표시(변경 없음). 신설하는 검색 기능은 (1) 먼저 내 보관함 안에서
   검색 → (2) 결과가 부족하면 gikka 전체(video 테이블, 등록 여부 무관)에서도 찾아
   "이런 것도 있어요" 로 보완 노출 → (3) 보완 노출된 항목에 "내 보관함에 등록" 버튼
   (URL 재입력 없이 해당 video_id로 내 registration만 새로 생성 — 재분석 없음, 기존
   "등록 시 이미 있으면 메타 생략" 경로와 동일한 성격).
   검색 대상 필드: tags(V4로 이미 저장 중) + title + recipe.name.
3. **추천 소스 확장**: 사용자 지적 — "등록 3개짜리 신규 사용자는 추천이 거의 안 뜬다,
   50개 쌓일 때까지 앱 쓸 이유가 없다". `RecommendController`의 후보 소스를
   "내가 등록한 것"에서 "gikka 전체 분석 완료 RECIPE 전부"로 확장(냉장고 매칭은 그대로
   개인 것 기준). 카드에 "내 보관함" 여부만 작은 배지로 구분, 남의 레시피가 추천되면
   상세 팝업에 위 2번과 같은 "내 보관함에 등록" 버튼 제공. `RegistrationRepository
   .recipesForUser` 사용을 `VideoRepository` 전체 조회로 교체(기존 3단계 판정·정렬
   로직은 `RecommendRules` 그대로 재사용, 후보 소스만 교체).
4. **재료/양념 사전 DB화 + 그룹 매칭 + 오너 관리/AI 점검** (2026-07-17 grill-me로 크게
   재구성 — 아래 "5차-4 사전·매칭 재설계" 절이 이 항목의 단일 원본. 4차의 "정규화·별칭
   병합 안 함"을 **명시적으로 뒤집었다**. 계기·근거는 그 절 참고).
- 콘텐츠 신고(보류 항목, 참고 기록): 향후 재검토 시 방향은 "AI가 스스로 애매함을 표시하는
  방식은 신뢰하지 않는다(LLM은 자기 확신을 실제 정확도와 무관하게 냄, 오늘 코르키 사례가
  근거) — 대신 사람이 발견하면 신고(오너 전용 여부는 미정) → 오너가 원본 대조 후 직접
  수정(video.summary/tags/category UPDATE, 이미 있는 오너 전용 API 패턴 재사용 가능,
  DB 구조상 장벽 없음)"이 유력 후보.

### 5차-4 사전·매칭 재설계 (2026-07-17 grill-me 확정 — 이 절이 단일 원본)
- 계기: 실사용에서 "추천에 매칭되는 레시피가 거의 없다". 두 원인으로 분해됨 —
  ㉠ **양념 오분류**: `RecommendRules.SEASONINGS` 가 하드코딩 19개뿐이라 그 외 장·소스가
  전부 MAIN 으로 잡혀 "부족 주재료"가 되고 레시피가 밀려남(위쪽 "완전 가능/양념만 부족"
  섹션이 텅 빔). ㉡ **변형 세밀 분리**: 쌀떡≠밀떡, 신라면≠사각라면 처럼 정확 매칭이라
  대체 가능한 스테이플이 안 잡힘.
- **4차 "정규화 안 함" 뒤집음**: 4차는 오병합 위험(진간장≠간장, 맛소금≠소금)을 이유로
  정규화를 미뤘다. 실사용 고통이 그 결정을 뒤집을 근거가 됐고, 이번엔 오병합을 막는
  안전장치(아래 오너 확정 큐·비대칭 규칙)가 함께 생기므로 미룰 이유가 사라졌다.
- **규모로 안 없어진다(사용자 우려에 대한 결론)**: "레시피가 10만 개면 확률적으로 맞겠지"는
  글로벌 후보(5차-3, 남의 레시피)에만 참이다. **본인 보관함**은 규모가 아무리 커도 내 30개가
  내 냉장고와 안 맞으면 0 — 그게 앱의 심장("저장한 걸 꺼내준다")이라 정규화가 필요하다.
  단 그룹이 커버할 실질 집합은 "자주 겹치는 대체 스테이플"(라면·떡·파·고기류 등) 소수라
  투자 규모는 작게 유지된다(희귀 재료는 애초에 매칭을 잘 안 막음).

- **사전 스키마(항목=재료 이름 1개당 1행)**: `(name, match_key, status)` — **양념 여부의 단일
  원본은 `status` 하나다** (2026-07-17 아키텍처 점검에서 tier 컬럼 제거, 아래 근거).
  - `status` 4종: PENDING(신규 자동생성) / SKIPPED(오너 "지금 모르겠음", 큐에서 안 사라짐) /
    CONFIRMED_MAIN / CONFIRMED_SEASONING. 이름 기준 dedupe.
  - **양념 여부 = status 의 파생**: 매칭이 읽는 "양념 이름 집합" = `WHERE status='CONFIRMED_SEASONING'`.
    그 외(판정 전 PENDING·SKIPPED·CONFIRMED_MAIN)는 전부 **주재료 취급**(안전 기본값 — 양념으로
    잘못 빼는 것보다 "부족 재료"가 덜 위험). 양념은 "양념만 부족" 섹션으로 살아남는다.
  - **tier 컬럼을 두지 않는 이유(2026-07-17)**: 초안은 tier(MAIN/SEASONING) 컬럼을 status 와 함께
    뒀으나, tier 는 status 의 순수 파생이라 컬럼이면 시드 SQL·updateStatus·confirmSeasoningIfPending·
    프론트 네 write 경로가 동기화를 짊어진다(얕은 확산). status 를 단일 원본으로 두고 파생을 없앴다.
  - `match_key` = "무엇이 있으면 이걸 가진 걸로 칠까?". **기본값 = 자기 이름**(안 묶으면 현행
    엄격 유지). 매칭 규칙 = 냉장고 이름과 레시피 이름의 `match_key` 가 같으면 "있음"(슬라이스2에서 활성).

- **LLM 확신 처리(tier)**: 분석 호출(Gemini·로컬 공통, 기존 분류에 필드만 추가)에 재료별
  "SEASONING 확신/UNSURE" 판정 요청. **확신 SEASONING → 자동 CONFIRMED_SEASONING**(양념
  분류는 저위험 폐쇄 판단, 오분류 최악값이 "부족 재료 표시"라 안전). UNSURE 만 오너 큐(PENDING).
  추가 비용 0(같은 1회 호출).
- **안전 비대칭 규칙(오병합 방지의 핵심)**: 쪼개기(기본 match_key=자기자신)는 자동/안전
  (틀려야 "덜 매칭"). **묶기(다른 그룹 합류)는 오직 오너 확정만** — LLM 은 후보 제안까지만,
  자동 병합 금지. 파프리카→파, 진간장→간장 같은 오병합이 사람 손 없이 절대 안 일어남.
  tier(자동확정)와 group(수동확정)을 위험도에 맞춰 분리한 것이 이 설계의 요체.
- **AI 일괄 점검(온디맨드 + 제안 큐 통합)**: 오너가 화면에서 `[AI 점검]` → 사전 전체
  (이름+tier+그룹)를 LLM(기존 배관 재사용)에 1회 전달 → 묶을 후보·재분류 후보를 **제안**으로
  큐에 적재. 자동 적용 없음, 이미 CONFIRMED 된 항목도 덮어쓰지 않고 "재검토 제안"으로만.
  스케줄러 아님(2인스턴스 멱등성·상시 한도 소모 회피 — 필요해지면 승격, 사후 비공개 감지
  스케줄러가 생기면 그 배관 재사용). 재료 이름 목록만 보고 묶는 건 폐쇄적 어휘 판단이라
  LLM 이 안정적으로 잘하는 일(코르키식 세계지식 추론과 성격이 다름 — 그래도 제안까지만).
- **오너 화면**: 기존 "오너 전용 기능은 `/recipe/monitor` 한 곳에 모은다"(2026-07-13) 정책에
  따라 monitor 에 사전 관리 섹션 통합 — 인라인 즉시 편집(tier·그룹) + 제안 큐 + `[AI 점검]` 버튼.
- **`RecommendRules.classify()`** 를 코드 상수(SEASONINGS/ALIASES) 대신 DB 사전 조회로 교체,
  `match()` 는 정확 이름 대신 `match_key` 비교로 교체.

- **구현 순서 — 수직 슬라이스 + 증거 게이트(2026-07-17 확정, scope reduction)**: 원안(풀세트
  일괄)을 믿음으로 밀지 않고, 값싼 고레버리지부터 배포해 증거로 다음을 판정한다.
  - **슬라이스1 — 사전 기반 + 양념 즉효(문제 ㉠)**: V11 스키마(match_key 컬럼은 처음부터 두되
    전부 자기자신) + 시드(기존 SEASONINGS/ALIASES + 기존 추출된 재료 이름 전부 스캔 → PENDING)
    + classify() DB 조회 교체(그룹 자기자신이라 주재료 동작 불변, 안전) + 추출 호출 SEASONING
    확신/UNSURE 판정 + monitor 최소판(목록·tier 인라인 수정·[AI 점검] tier 제안). 배포·폰 검증.
  - **슬라이스2 — 그룹 매칭(문제 ㉡)**: monitor 에 그룹 병합 관리 + AI 점검을 병합 제안까지
    확장(병합은 오너 확정만) + match() 를 match_key 비교로 교체.
  - **증거 게이트**: 슬라이스2(그룹 UI·AI 병합점검) 착수 여부는 **슬라이스1 배포 후에도 변형
    문제가 남는지 측정해 재결정**한다. 스키마에 match_key 만 심어두면 나중 확장 비용이 낮아
    미리 다 짓지 않아도 된다. 근거: 지금 "거의 없다"의 상당 부분이 그룹이 아니라 tier 문제일
    공산이 커, 슬라이스1 만으로 레시피가 아래 섹션에서 위로 올라와 체감될 가능성이 높다.
- 착수 전 필수(기존 지침): `gitnexus impact` 로 `classify()` 호출부 전수 확인, 순수 함수
  테스트(`RecommendRulesTest`)를 DB 시임/Repository 레벨로 재설계, ArchUnit 격리 유지.


1. 코드 격리: 백엔드는 `domain/recipe` 패키지 안에서만. 다른 도메인과 상호 참조 금지.
   프론트는 `frontend/src/domain/recipe/`에 격리.

     Google 로그인, /api/recipe API, 냉장고 저장소 교체.
     성공 기준: 냉장고 화면 코드 무수정으로 저장소 구현체만 교체됨.
3차: Gemini 추출 + 등록 화면 (URL 개별 + 재생목록 일괄, 대기열) — 추출 품질 검증 지점.
     PWA Share Target 등록 포함 (공유 메뉴 → 기까 → 즉시 분석).
     (2026-07-11 조사) 최신 Gemini는 media_resolution 파라미터로 프레임당 토큰을 조절 가능 —
     쇼츠는 저해상도로 시작해 품질 부족 시에만 올린다 (무료 한도 절약).
     요청당 영상 10개까지 가능하나 품질·오류 격리를 위해 1영상 1요청 원칙 유지, 필요 시 재검토.
     대기열은 DB 테이블(대기/분석중/완료/실패) + 단일 워커로 구현 — 별도 큐 인프라 없음.
     병목은 Gemini 분당 한도이므로 다중 사용자가 돼도 같은 구조를 유지한다.
4차: 레시피 목록·상세 + 추천 화면 (샘플이 아닌 실제 추출 데이터로)
5차: 품질 향상 + 다중 사용자 준비 (2026-07-14 grill-me로 재구성 — 상세는 위 "5차 확장" 절.
     "자주 사는 재료 버튼"은 이미 2차에서 완료 확인돼 범위에서 빠짐. 순서: 1) ETC/TIP
     프롬프트 안전화 2) 보관함 검색+gikka 전체 보완 3) 추천 소스 확장 4) 재료/양념 사전+
     오너 판정 큐. 착수 계기: 실사용 배포 후 소수 친구에게 PWA 설치를 안내할 계획이 임박해
     콜드스타트·품질 문제를 먼저 처리해야 함)
6차: 릴스·틱톡 확장 (2026-07-11 확정) — 착수 조건은 유튜브 추출 품질 합격뿐.
     방식: 서버에서 yt-dlp로 영상 다운로드(임시, 분석 후 삭제) → Gemini File API 업로드 →
     기존 추출 프롬프트 재사용. 규율 4의 추출 인터페이스에 platform별 구현체만 추가
     (스키마·화면 변경 없음 — platform 필드 선반영 덕분).
     첫 작업: yt-dlp로 본인 릴스·틱톡 링크 실제 다운로드 테스트.
     인스타 쿠키 운영 방식 (2026-07-11 확정 — 무인 운영 목표, 유료 서비스 안 씀):
     - mac-mini 크롬에 인스타 전용 프로필을 만들어 로그인 유지,
       yt-dlp는 --cookies-from-browser chrome으로 그 프로필에서 쿠키를 직접 읽음
       (쿠키 파일 내보내기·수동 갱신 단계 자체를 제거. 첫 실행 시 macOS 키체인 접근 허용 1회 필요).
     - 세션 유지: launchd 주 1회 `open -a "Google Chrome" --profile-directory=... instagram.com`
       으로 페이지만 터치 (진짜 크롬·진짜 프로필이라 봇 탐지 불가).
     - 유효성 체크는 사용 직전 + 일 1회. 매분 체크 금지 — 기계적 반복 접근이 봇 신호가 되어
       쿠키 수명을 오히려 줄임. 실패 시 텔레그램 알림 → 사람은 재로그인만 (드묾).
     - 로그인 자동화(아이디·비번 스크립트 입력) 금지 — 봇 탐지 최우선 표적, 계정 정지 위험.
       Playwright/Selenium으로 브라우저 조종도 같은 이유로 안 씀 (자동화 지문 감지됨).
     참고 구현: github.com/pickeld/social_recipes — 동일 문제·동일 파이프라인(yt-dlp→LLM)의
     오픈소스. 쿠키 관리가 심하게 귀찮아지면 Apify류 유료 스크래핑이 대안(개인용엔 과함).

## 5. 리스크 (인지한 상태로 진행)
- Gemini URL 기능은 프리뷰: 정책 변경 시 yt-dlp 다운로드+업로드 방식으로 교체 (규율 4로 대비).
- 추출 품질 미검증: 5차에서 검증. 부족하면 프롬프트·해상도 조정 → 그래도 안 되면 유료 모델 소액(영상당 10~15원) 재논의.
- 유튜브가 유사 기능 출시 가능성: 개인 도구 가치는 불변. 상용화 판단 시점에 재평가.
- 무료 등급 한도: 일 약 250~1,500요청, 분당 약 10요청, 유튜브 URL 일 8시간 분량.
