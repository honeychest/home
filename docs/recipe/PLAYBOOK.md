# recipe — PLAYBOOK (단계별 작업 가드레일)

> 이 문서는 "각 단계를 어떻게 작업해야 하는가"를 담는다.
> 결정은 CONTEXT.md, 상태는 progress.html에 있다.
> 끝난 단계의 절은 삭제한다 (문서 비대화 방지).

## 공통 규칙 (모든 단계)

### 착수 전 grill-me 점검 (필수 — 이것 없이 구현 시작 금지)
새 단계를 시작하기 전, grill-me 스킬을 이용해 "지금까지 구현된 실물"을 근거로
사용자와 다음을 확인하고 합의한 뒤에만 구현을 시작한다:
1. 의도 확인: 이번 단계에서 만들려는 것이 사용자 의도와 여전히 일치하는가
2. 변경 여부: 직전 단계 결과물을 써보니 바꾸고 싶어진 것이 있는가
3. 추가 결정: 이번 단계에서 새로 정해야 할 갈림길 (한 번에 하나씩 질문)
4. 위험: 이번 단계의 리스크와 대비책
5. 추천: 더 나은 방식이 보이면 장단점과 함께 제안

### 작업 규칙
- 쓰기·삭제·편집·생성 툴은 사용자 응답에 '승인' 문자열이 포함된 경우에만 사용.
  예외: `docs/recipe/` 안의 문서 3종 갱신은 사전 승인된 것으로 본다.
- 단계 완료 또는 중단 시 progress.html(체크리스트·다음 할 일·갱신일) 갱신.
- 화면 스타일 수정은 화면 코드가 아니라 tokens.css 또는 ui/ 킷에서 (recipe 내부 일관성).
- 기존 심볼(다른 도메인 포함) 수정 시 GitNexus 영향 분석 필수 (프로젝트 공통 규칙).
- UI 문제 제보 처리 절차 (2026-07-09 확정): 사용자가 화면 이상을 제보하면
  추측으로 원인을 확정하지 않는다. 먼저 rcp- 이름 체계로 위치를 특정하는 질문
  ("rcp-frequent-edit-toggle 버튼인가요?")과 스크린샷을 요청해 증상을 확정하고,
  원인 가설을 사용자에게 확인받은 뒤에 수정한다. UI는 실기기를 보는 사용자가
  가장 정확한 관찰자다. AI의 헤드리스 캡처는 보조 수단일 뿐 판단 근거로 삼지 않는다.

### UI 품질 기본선 (모든 화면·컴포넌트에 자동 적용 — 사용자가 지시하지 않아도 AI 책임)
사용자는 "감성 판단"만 한다. 아래는 전문 직군이라면 당연히 챙기는 항목이므로
AI가 만들 때 적용하고, 보고 전에 스스로 검증한다. 어긴 채 발견되면 킷/토큰 레벨에서 고친다.
1. 다국어·긴 글자: 글자 길이 2~3배에도 안 깨짐 (버튼·칩 줄바꿈 금지, 탭 말줄임,
   이름류는 행 내 줄바꿈). 고정 너비 금지, min-height만. 검증: /recipe/styleguide
   "긴 글자 스트레스 테스트" 절 — 새 공용 컴포넌트마다 긴 문자열 케이스 의무 추가.
2. 두 테마: 라이트/다크 모두에서 확인. 색은 tokens.css 변수만 사용하므로
   변수 밖 색을 쓰는 순간 이 항목 위반.
3. 터치: 모든 탭 가능한 요소는 최소 44px(--rcp-touch). 아이콘만 있는 버튼은 aria-label.
4. 세 가지 상태: 목록·데이터 화면은 빈 상태 / 로딩 / 에러 상태를 처음부터 설계.
5. 폰 환경: safe-area(제스처 바) 대응, 키보드가 올라올 때 입력창 가림 확인,
   시스템 글자 크게 설정(접근성)에서도 레이아웃 유지.
6. 비보안 컨텍스트: http LAN 접속에서는 crypto.randomUUID·클립보드 API 등이 없음 —
   브라우저 전용 API 사용 시 폴백 필수.
7. 문구/데이터 분리: UI 문구("오래된 재료부터 보여줘요")를 데이터(재료명·날짜)에
   섞지 않는다. i18n 도입(영어 고도화) 시 문자열 추출이 가능해야 하므로.
   문구를 조합할 때 어순을 코드로 박는 것("재료 " + n + "개 있음"式 하드코딩 연결)도 피한다.
8. 검증 방법: 보고 전에 AI가 직접 화면을 띄워(브라우저/스크린샷) 확인한다.
   "빌드 통과"는 검증이 아니다.
이 목록은 깨짐이 새로 발견될 때마다 항목을 추가하는 살아있는 목록이다.

## 1차: 디자인 기반 + 냉장고 화면

### 코딩 전 디자인 인터뷰 (필수 — 이 순서대로)
1. frontend-design 스킬을 로드하고 시작한다.
2. 사용자에게 참고 링크를 제시하고 "어떤 느낌·색감을 원하는지" 묻는다:
   - SuperCook: https://www.supercook.com/
   - 만개의레시피: https://m.10000recipe.com/
   - 냉쉐프 (앱스토어): https://apps.apple.com/us/app/id6757459377
   - 냉장고 파먹기 (구글플레이): https://play.google.com/store/apps/details?id=com.lazyheroes.erfe
   - Pantry Pic: https://pantrypic.com/
3. 색감·분위기 방향을 2~3개 시안으로 제시하고, 사용자가 고른 결과를
   tokens.css로 고정한다. (recipe 앱만의 새 디자인. 기존 home 디자인과 맞출 필요 없음)
4. 폰(S25)에서 화면에 접근할 경로를 사용자와 확정한다
   (예: 같은 와이파이에서 이 PC의 개발 서버 접속 / mac-mini에 배포 후 접속).
   이것이 정해져야 "폰 홈화면 추가해 실사용"이라는 1차 완료 기준이 성립한다.

### 구현 규칙
- S25 모바일 뷰포트 기준. 데스크톱 대응 금지 (시간 낭비).
- 순서: tokens.css → ui 킷 + /recipe/styleguide 페이지 → 저장소 인터페이스
  + localStorage 구현체 → 냉장고 화면.
- 냉장고 화면 스펙은 CONTEXT.md "냉장고" 절 준수 (오래된 순, 즉시 삭제, 임박 토글,
  이름·날짜 수정, 재등록 시 날짜 갱신).
- 완료 기준: 폰 홈화면에 추가해 냉장고 관리를 실사용할 수 있다.

## 2차: 레시피 목록·상세 + 추천 화면
- 규칙 재확인: 1층 "지금 가능" 최대 5개(임박 재료 사용 최상단 → 오래된 재료 순)
  + 2층 "하나만 사면" 최대 3개(+살 재료 표시). 특이양념은 판정 제외·경고 표시.
- 샘플 레시피는 사용자의 실제 냉장고 재료와 겹치게 구성한다 (실감 테스트가 목적).
- 화면 시안은 사용자에게 보여주고 피드백을 받은 후 확정한다.

## 3차: 등록 화면
- URL 입력·일괄 등록 진행률 UI. 동작은 흉내(가짜)임을 UI에 명시한다.

## 4차: 백엔드 연결
- CONTEXT.md "분리 규율 5가지" 재확인 후 시작 (전용 DB, /api/recipe, 패키지 격리).
- 화면에 로딩/에러 상태 추가 (품질 기본선 4번의 미충족분 — localStorage는 즉시 응답이라
  1~3차에서는 생략했음. API 전환 시 지연·실패가 실제로 생기므로 이 시점에 필수).
- localStorage에 쌓인 실사용 데이터(냉장고)를 DB로 옮길지 사용자에게 질문.
- 냉장고부터 저장소 구현체 교체. 화면 코드는 수정되지 않아야 정상
  (수정이 필요하다면 인터페이스 설계가 잘못된 것 — 원인부터 확인).

## 5차: Gemini 추출 + 재생목록 일괄 등록
- 사용자 준비물 먼저 확인: Gemini API 키 발급, 재생목록 "일부공개" 전환.
  해당 구글 프로젝트에 결제 연결 금지 (무료 등급 소멸).
- Gemini 호출은 인터페이스 뒤에 격리 (URL 프리뷰 정책 변경 대비).
- 무료 한도(분당 약 10회) 준수: 대기열 + 429 시 대기 후 자동 재개 + 진행률 표시.
- 추출 결과 첫 몇 개는 사용자와 함께 검수. 품질 부족 시: 프롬프트·해상도 조정
  → 그래도 부족하면 유료 모델 소액(영상당 10~15원) 사용을 다시 논의.

## 6차: 다듬기
- 사용자에게 실사용 불만 목록을 먼저 받고, 그 순서대로 작업한다.
