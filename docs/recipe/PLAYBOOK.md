# recipe — PLAYBOOK (단계별 작업 가드레일)

> 이 문서는 "각 단계를 어떻게 작업해야 하는가"를 담는다.
> 결정은 CONTEXT.md, 상태는 progress.html에 있다.
> 끝난 단계의 절은 삭제한다 (문서 비대화 방지).

## 공통 규칙 (모든 단계)

### 착수 전 grill-me 점검 (필수 — 이것 없이 구현 시작 금지)
새 단계를 시작하기 전, grill-me 스킬을 이용해 "지금까지 구현된 실물"을 근거로
사용자와 다음을 확인하고 합의한 뒤에만 구현을 시작한다:
1. 의도 확인: 이번 단계에서 만들려는 것이 사용자 의도와 여전히 일치하는가
2. 변경 여부: 직전 단계 결과물을 써보니 바꾸고 싶어진 것이 있는가
3. 추가 결정: 이번 단계에서 새로 정해야 할 갈림길 (한 번에 하나씩 질문)
4. 위험: 이번 단계의 리스크와 대비책
5. 추천: 더 나은 방식이 보이면 장단점과 함께 제안

### 작업 규칙
- 쓰기·삭제·편집·생성 툴은 사용자 응답에 '승인' 문자열이 포함된 경우에만 사용.
  예외: `docs/recipe/` 안의 문서 3종 갱신은 사전 승인된 것으로 본다.
- 단계 완료 또는 중단 시 progress.html(체크리스트·다음 할 일·갱신일) 갱신.
- 화면 스타일 수정은 화면 코드가 아니라 tokens.css 또는 ui/ 킷에서 (recipe 내부 일관성).
- 기존 심볼(다른 도메인 포함) 수정 시 GitNexus 영향 분석 필수 (프로젝트 공통 규칙).
- UI 문제 제보 처리 절차 (2026-07-09 확정): 사용자가 화면 이상을 제보하면
  추측으로 원인을 확정하지 않는다. 먼저 rcp- 이름 체계로 위치를 특정하는 질문
  ("rcp-frequent-edit-toggle 버튼인가요?")과 스크린샷을 요청해 증상을 확정하고,
  원인 가설을 사용자에게 확인받은 뒤에 수정한다. UI는 실기기를 보는 사용자가
  가장 정확한 관찰자다. AI의 헤드리스 캡처는 보조 수단일 뿐 판단 근거로 삼지 않는다.

### UI 품질 기본선 (모든 화면·컴포넌트에 자동 적용 — 사용자가 지시하지 않아도 AI 책임)
사용자는 "감성 판단"만 한다. 아래는 전문 직군이라면 당연히 챙기는 항목이므로
AI가 만들 때 적용하고, 보고 전에 스스로 검증한다. 어긴 채 발견되면 킷/토큰 레벨에서 고친다.
1. 다국어·긴 글자: 글자 길이 2~3배에도 안 깨짐 (버튼·칩 줄바꿈 금지, 탭 말줄임,
   이름류는 행 내 줄바꿈). 고정 너비 금지, min-height만. 검증: /recipe/styleguide
   "긴 글자 스트레스 테스트" 절 — 새 공용 컴포넌트마다 긴 문자열 케이스 의무 추가.
2. 두 테마: 라이트/다크 모두에서 확인. 색은 tokens.css 변수만 사용하므로
   변수 밖 색을 쓰는 순간 이 항목 위반.
3. 터치: 모든 탭 가능한 요소는 최소 44px(--rcp-touch). 아이콘만 있는 버튼은 aria-label.
4. 세 가지 상태: 목록·데이터 화면은 빈 상태 / 로딩 / 에러 상태를 처음부터 설계.
5. 폰 환경: safe-area(제스처 바) 대응, 키보드가 올라올 때 입력창 가림 확인,
   시스템 글자 크게 설정(접근성)에서도 레이아웃 유지.
6. 비보안 컨텍스트: http LAN 접속에서는 crypto.randomUUID·클립보드 API 등이 없음 —
   브라우저 전용 API 사용 시 폴백 필수.
7. 문구/데이터 분리: UI 문구("오래된 재료부터 보여줘요")를 데이터(재료명·날짜)에
   섞지 않는다. i18n 도입(영어 고도화) 시 문자열 추출이 가능해야 하므로.
   문구를 조합할 때 어순을 코드로 박는 것("재료 " + n + "개 있음"式 하드코딩 연결)도 피한다.
8. 검증 방법: 보고 전에 AI가 직접 화면을 띄워(브라우저/스크린샷) 확인한다.
   "빌드 통과"는 검증이 아니다.
이 목록은 깨짐이 새로 발견될 때마다 항목을 추가하는 살아있는 목록이다.

## 2차: 백엔드 기반 (DB·로그인·API·저장소 교체)
- CONTEXT.md "분리 규율" 8가지 재확인 후 시작 (전용 DB·DataSource, /api/recipe,
  패키지 격리, ArchUnit 감시, 공용 코드 복사 소유).
- DB는 기존 chs-pgvector 컨테이너 안에 `gikka` 데이터베이스 + 전용 계정 `gikka`
  (gikka DB만 접근 권한). 새 컨테이너 만들지 말 것 (2026-07-10 확정).
- 첫 작업 = ArchUnit 격리 테스트 작성 (규율을 빌드가 지키게 한 뒤 코드 시작).
- 사용자 준비물 먼저 확인: Google OAuth 클라이언트 생성 (Gemini용 결제 미연결
  구글 프로젝트에 recipe 전용으로 — 결제 연결 금지).
- 인증: CONTEXT.md "인증" 절 준수 — GIS ID 토큰 → 백엔드 검증 → recipe 자체 세션.
  `/api/recipe/**` 전용 SecurityFilterChain, 기존 SecurityConfig 무접촉.
- 화면에 로딩/에러 상태 추가 (품질 기본선 4번의 미충족분 — localStorage는 즉시 응답이라
  1차에서는 생략했음. API 전환 시 지연·실패가 실제로 생기므로 이 시점에 필수).
- localStorage 냉장고 데이터는 DB로 이관하지 않는다 (2026-07-10 사용자 확정 — 새로 입력.
  이관 코드 만들지 말 것).
- 냉장고부터 저장소 구현체 교체. 화면 코드는 수정되지 않아야 정상
  (수정이 필요하다면 인터페이스 설계가 잘못된 것 — 원인부터 확인).
- 서버 제약 주의: 이 프로젝트 서버는 앱 2인스턴스 + 작은 힙(512M) + 작은 커넥션 풀.
  recipe 전용 DataSource의 풀 크기는 작게(2~3) 시작한다.
- 아키텍처 관례 (2026-07-10 점검 확정 — 3·4차의 새 API·화면도 반드시 따를 것):
  1. 인증 필요한 recipe API 는 컨트롤러 파라미터에 `@GikkaUserId long userId` 선언.
     리졸버가 미로그인 401 을 처리하므로 본문에 인증 코드를 쓰지 않는다.
     사용자 식별은 CurrentUser 인터페이스의 어댑터 2개(JwtCurrentUser=쿠키 JWT,
     DevCurrentUser=local 전용 dev 폴백)로 분리 — dev 폴백은 prod 프로파일이면
     기동 자체가 실패한다 (CurrentUserConfigTest 가 고정. 주석이 아니라 테스트가 지킴).
  2. 프론트 데이터 저장소는 `data/http.ts` 의 request() 사용 — 세션 만료(401)가
     셸 게이트로 전달되어 로그인 화면 전환. 저장소·화면은 인증을 모른다.
     (예외: authRepository — 401 이 정상 응답이라 자체 fetch)
  3. 서비스 계층 없음 — 저장소 모듈(예: FridgeRepository)에 SQL·트랜잭션·동작 규칙 집중.
     DB 없이 검증할 로직은 static 순수 함수로 빼서 테스트 (예: rankFrequent).
  4. 외부 HTTP 호출은 RestClient.Builder 주입으로 만들어 MockRestServiceServer 테스트 시임 확보.
  5. 화면의 조작 핸들러(추가·삭제·수정)는 화면당 하나의 실행기(runMutation — FridgePage 참고)로
     감싼다: 실패 문구·연타 방지·서버 재동기화를 한 곳에. 문구는 프론트 소유 (CONTEXT.md 에러 계약).
  6. 도메인 판정(선반 분류 등)은 화면이 아니라 순수 모듈(data/fridgeShelves.ts 패턴)에 두고
     vitest 로 고정한다 (frontend: npm run test). 화면은 결과만 렌더.
- 함정 (2026-07-10 실측): TransactionManager 를 recipe 쪽 스프링 빈으로 등록 금지 —
  부트의 기본 transactionManager 자동 구성이 꺼져 기존 도메인 @Transactional 전체가 깨진다.
  gikka 트랜잭션은 GikkaDataSourceConfig 의 TransactionTemplate(빈 이름 gikkaTxTemplate)로만.
- 검증 팁: 한글 JSON body 를 Windows 셸 curl -d 로 보내면 CP949 로 깨져 가짜 500이 난다.
  UTF-8 파일 + --data-binary @파일 로 호출할 것.

## 3차: Gemini 추출 + 등록 화면 (grill-me 완료 2026-07-12 — 결정은 CONTEXT.md 레시피 절)
- 진행 순서 (2026-07-12 사용자 확정): (1) 등록 화면 UI — 목 저장소로 전 상태
  (대기/분석중/완료/레시피 아님/너무 김/실패) 표현 → (2) 폰 검수 →
  (3) 백엔드: 메타 조회(YouTube Data API)·대기열(DB 테이블+단일 워커)·Gemini 추출 →
  (4) 저장소 교체(화면 무수정이어야 정상) → (5) 품질 검수 배치 10개 채점.
- 사용자 준비물: Gemini 키 완료(gikka 프로젝트). 남은 것 = gikka 프로젝트에
  YouTube Data API 켜기, 재생목록 "일부공개" 전환(일괄 등록 검증 전까지),
  Share Target 검증 시 PWA 재설치. 결제 연결 금지 (무료 등급 소멸).
- 파이프라인·길이 컷(7분)·레시피 판정·재시도 정책·합격 기준(10중 8)은 CONTEXT.md 참고.
- Gemini 호출은 인터페이스 뒤에 격리 (URL 프리뷰 정책 변경 대비). 메타 조회도
  플랫폼별 인터페이스 (6차 yt-dlp 가 같은 자리에 꽂힘).
- 무료 한도(분당 약 10회) 준수: 대기열 + 429 시 대기 후 자동 재개 + 진행률 표시.
- 등록 화면: URL 개별 추가 + 재생목록 일괄 등록 + 진행률 (이번엔 실동작).
  영상 ID 파서로 중복 판별 (youtu.be/, watch?v=, /shorts/ 등) — 순수 모듈 + vitest (관례 6번).
- 재료는 원문 그대로 저장 — 재료 사전·정규화를 이 단계에 만들지 말 것 (4차 직전 도입).
- 검수용 결과 보기: 대기열 항목 탭 → 추출 결과 시트 (정식 목록·상세는 4차에서 대체).
- 홈 섬네일 한 줄 포함. Share Target 은 배포 후에만 검증 가능 (http 개발 서버 불가).
- 추출 결과 첫 몇 개는 사용자와 함께 검수. 품질 부족 시: 프롬프트·해상도 조정
  → 그래도 부족하면 유료 모델 소액(영상당 10~15원) 사용을 다시 논의.
