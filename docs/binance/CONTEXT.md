# binance 자동매매 — CONTEXT

> 코드·그래프(GitNexus)가 줄 수 없는 것만 담는다 — 도메인 의미, 불변 규칙, 설계 '이유'.
> **2026-09-01 기준 PoC(가능성 확인) 단계 — 실제 구현 코드는 아직 없다.**
> 이 저장소엔 이미 실시간 바이낸스 인프라(`springboot`의 kline 수집·watchdog,
> `frontend/src/page/binance`·`page/trade`·`page/signal`)가 있고, 자동매매는 그 위에 얹는다.
> nexus(별도 서브프로젝트, 텔레그램 개인비서 봇)와는 무관 — 처음에 nexus에 두려다 정정함
> (오너는 원래도 이 lab 저장소의 기존 인프라 위에 만들려던 것이었음).

## 1. 정의
바이낸스 **선물(futures)** 자동매매. 오너는 선물만 거래하며 spot은 취급하지 않는다.
기존 binance 실시간 인프라(kline 수집)를 데이터 소스로 재사용하고, 그 위에 시그널 판정 +
주문 실행 로직을 추가하는 것이 목표.

## 2. 핵심 제약
- **spot과 선물은 완전히 다른 API/데이터다.** spot(`api.binance.com`)과 선물
  (`fapi.binance.com`)은 별개 엔드포인트고, 같은 시각의 캔들이라도 값이 다를 수 있다
  (청산 와이드 등). **오너는 선물만 쓰므로 모든 조회·계산·주문은 선물 API/데이터로만 한다.**
  2026-09-01 PoC 세션에서 spot으로 계산했다가 오너가 정정한 실측 사고 있음.
- **실거래(주문 발행)로 이어지는 코드는 아래 안전 원칙 넷을 전부 충족해야 활성화한다**
  (2026-09-01 확립 — 근거는 §5):
  1. 시간 값 하드코딩 금지, 실행 시점에 서버 시간에서 직접 파생
  2. 매 판단 주기마다 데이터 신선도 검증(최근 캔들 시각이 지금과 충분히 가까운지) —
     벗어나면 판단 중단 + 알림
  3. 주문 실행 직전 최종 안전핀 — 계산값이 실시간 시세와 크게 어긋나면 실행 중단
  4. 전략 로직과 분리된 킬스위치 — 연속 오류·이상치 감지 시 전체 중단 + 알림
- **트레이딩뷰는 자동화 API가 없다.** 참고용 시각화로만 쓰고, 실제 데이터·주문은 바이낸스 API
  직접 연동으로 한다.

## 3. 기존 인프라 현황 (요약 — 상세는 GitNexus·`docs/generated/be-binance.md`)
- 실시간 WebSocket kline 수집 + watchdog/재연결 안정화 이미 구축됨 (`BinanceWebSocketStream` 등).
- **agg_trade(원시 체결 틱) 실시간 수집을 시도했다가 데이터량 폭발(쓰기폭발)과 소켓 불안정으로
  포기하고, 최근 kline 1초~1분봉 기준으로 축소한 이력이 있다**(오너 서술, 2026-09-01).
  관련 커밋: `perf(binance): stop raw_agg_trade writes and disable related archiving`,
  `feat(binance): add Binance kline-sourced 1m candle shadow pipeline`.
  ⇒ **새 시그널 로직도 틱 단위가 아니라 kline(분/시간봉) 단위를 기본으로 설계한다.**
- `frontend/src/page/trade`·`page/signal`·`page/analysis`: 기존 시각화 화면. 원래 자동매매
  목적으로 시작했으나 시그널 방향을 못 정해 이런저런 지표를 실험적으로 붙이다 목적이 흐려진
  이력이 있다(오너 표현: "이상한 사이트가 되어버렸다"). **새 시그널은 여러 개를 한꺼번에 붙이지
  말고, 하나를 정의→백테스트→검증까지 끝낸 뒤에만 다음으로 넘어간다** (§5 참고).

## 4. 불변 규칙(invariant)
- 선물 전용. spot 엔드포인트/데이터 사용 금지 (§2).
- 실거래 코드는 §2의 안전 원칙 4가지 없이 활성화하지 않는다.
- 시그널은 한 번에 하나만 검증한다 — 여러 지표를 동시에 실험적으로 붙이지 않는다(§3 이력 참고).

## 5. 설계 결정과 이유 (2026-09-01 PoC 세션)
- **트레이딩뷰 대신 바이낸스 API 직접 연동**: 트레이딩뷰는 임의 조건 자동 실행 API가 없고,
  Pine Script는 순매수/순매도 계산에 필요한 taker buy/sell 분리 볼륨에 애초에 접근할 수 없다
  (총 거래량만 제공). OI·CVD 같은 기본 제공 지표도 있지만 시각적 참고용이고, 정밀한 커스텀
  임계값 계산엔 바이낸스 원본 API가 필요.
- **스윙 고점/저점은 고정 lookback 봉 개수가 아니라 ZigZag(가격 %) 방식으로 판정**: "몇 봉
  안에 잡힐지" 문제(40봉이냐 60봉이냐)가 원천적으로 생기지 않는다. 예시 검증(2026-07-01 저점
  $57,800 ~ 2026-08-28 고점 $81,478, 4시간봉, 선물)에서 임계값 7.5% 이상이어야 중간 되돌림
  없이 그 둘만 스윙포인트로 잡혔다 — **임계값은 구간마다 다시 캘리브레이션 필요, 고정값 아님.**
- **평행채널(baseline 저점 2개 + 평행선)도 계산 가능하나, 두 저점의 시간 간격이 중요하다**:
  간격이 좁으면(실측: 12시간) 며칠 뒤로 외삽할 때 오차가 기하급수적으로 커져 무의미한 값이
  나온다(실측: 12시간 간격 저점으로 9일 외삽 → 채널 하단이 $49,212로 붕괴, 현재가와 무관한 값).
  **baseline이 그 구간 내 어떤 캔들에도 하향 이탈되지 않았는지를 검증 조건으로 둔다** — 실제
  지지선이었는지 확인하는 최소한의 필터.
  추세 방향(상승/하락) 판정은 다우이론 방식(최근 고점·저점이 각각 이전보다 높은지/낮은지)을
  ZigZag 결과에 바로 적용해서 구하고, 채널의 baseline을 저점(상승추세)/고점(하락추세) 중 어느
  쪽에 둘지를 그걸로 정한다. 고점·저점 신호가 엇갈리면(혼조) 채널 신호를 내지 않는다.
- **백테스트용 과거 데이터는 내부 DB에 의존하지 않는다**: 바이낸스 선물 REST API가 상장 시점부터
  전체 과거 캔들을 무료·무인증으로 제공하므로, DB 보유 기간이 짧아도 필요한 기간을 그때그때
  API로 받아 쓰면 된다.

## 6. 아직 안 끝난 것 (다음 세션에서 이어감)
- **채널 baseline으로 쓸 저점 2개(또는 고점 2개)를 사람 개입 없이 자동으로 고르는 규칙이 없다.**
  이번 PoC는 전부 오너가 차트에서 직접 짚은 값을 코드가 재현·검증하는 방식이었다. 후보:
  최소 시간 간격 강제 / 더 큰 ZigZag 임계값 사용 / "구간 내 이탈 없는 저점 쌍" 자동 탐색.
  다음 세션에서 규칙 하나를 정하고, 과거 여러 구간에 돌려 오너가 손으로 고를 점과 일치하는지
  검증부터 한다.
- **구현 위치가 springboot 내 어디일지 미정** — 기존 binance 도메인 패키지 구조를 아직 안 봤다.
  착수 전에 GitNexus로 기존 구조부터 파악할 것.
- 순매수/순매도(order flow) 시그널은 §3의 "혼조 신호" 경험상 단독으로는 노이즈가 크다고 판단,
  구조적 신호(채널 브레이크아웃 등)를 먼저 검증하기로 함 — 최종 결정은 아니고 우선순위일 뿐.
