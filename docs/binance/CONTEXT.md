> (오너는 원래도 이 lab 저장소의 기존 인프라 위에 만들려던 것이었음).

## 1. 정의
바이낸스 **선물(futures)** 자동매매. 오너는 선물만 거래하며 spot은 취급하지 않는다.
현재 단계는 기존 binance 실시간 인프라(kline 수집)를 데이터 소스로 재사용하는 정보성 도구다.
4개 인터벌의 시장 상태를 로컬 LLM이 읽기 전용 툴로 분석하며, 주문 실행은 향후 별도 단계다.

## 2. 핵심 제약
- **spot과 선물은 완전히 다른 API/데이터다.** spot(`api.binance.com`)과 선물
  (`fapi.binance.com`)은 별개 엔드포인트고, 같은 시각의 캔들이라도 값이 다를 수 있다
  (청산 와이드 등). **오너는 선물만 쓰므로 모든 조회·계산·주문은 선물 API/데이터로만 한다.**
  2026-09-01 PoC 세션에서 spot으로 계산했다가 오너가 정정한 실측 사고 있음.
- **실거래(주문 발행)로 이어지는 코드는 아래 안전 원칙 넷을 전부 충족해야 활성화한다**
  (2026-09-01 확립 — 근거는 5장):
  1. 시간 값 하드코딩 금지, 실행 시점에 서버 시간에서 직접 파생
  2. 매 판단 주기마다 데이터 신선도 검증(최근 캔들 시각이 지금과 충분히 가까운지) —
     벗어나면 판단 중단 + 알림
  3. 주문 실행 직전 최종 안전핀 — 계산값이 실시간 시세와 크게 어긋나면 실행 중단
  4. 전략 로직과 분리된 킬스위치 — 연속 오류·이상치 감지 시 전체 중단 + 알림
- **트레이딩뷰는 자동화 API가 없다.** 참고용 시각화로만 쓰고, 실제 데이터·주문은 바이낸스 API
  직접 연동으로 한다.

## 3. 기존 인프라와 현재 분석 도구 현황 (요약 — 상세는 GitNexus·`docs/generated/be-binance.md`)
- 실시간 WebSocket kline 수집 + watchdog/재연결 안정화 이미 구축됨 (`BinanceWebSocketStream` 등).
- `LiveMarketDataService`가 BTCUSDT 선물의 1m·5m·15m·4h 확정봉을 인터벌별 1000개씩
  인메모리로 유지하고, 리더 노드에서만 백필·WebSocket 연결을 수행한다.
- `BinanceKlineRestClient.fetchLatestClosedFutures`는 선물 서버 시각을 먼저 읽고 진행 중인 봉을
  제외한 뒤에만 `seed`에 넘긴다. 이 경로는 spot 메서드와 시그니처를 공유하지 않는다.
- `MarketSnapshotCalculator`와 공개된 `RsiCalculator`·`MacdCalculator`·`SupertrendCalculator`는
  라이브 버퍼를 모르는 순수 계산 계층이다. 정렬·중복·간격 검증과 최근 시계열을 제공하므로
  백테스트 입력에도 같은 계약을 재사용한다.
- `BinanceAutoTradeAnalysisService`는 DB 기록 없이 최신 자동 요약만 메모리에 보관하고,
  관리자 질문의 최근 대화는 브라우저 메모리에서만 받는다. 분석 전용 ChatClient에는
  `getCandles`·`getIndicatorHistory`·`getOrderFlow` 읽기 전용 툴만 등록된다.
- **agg_trade(원시 체결 틱) 실시간 수집을 시도했다가 데이터량 폭발(쓰기폭발)과 소켓 불안정으로
  포기하고, 최근 kline 1초~1분봉 기준으로 축소한 이력이 있다**(오너 서술, 2026-09-01).
  관련 커밋: `perf(binance): stop raw_agg_trade writes and disable related archiving`,
  `feat(binance): add Binance kline-sourced 1m candle shadow pipeline`.
  따라서 **새 시그널 로직도 틱 단위가 아니라 kline(분/시간봉) 단위를 기본으로 설계한다.**
- `frontend/src/page/trade`·`page/signal`·`page/analysis`: 기존 시각화 화면. 원래 자동매매
  목적으로 시작했으나 시그널 방향을 못 정해 이런저런 지표를 실험적으로 붙이다 목적이 흐려진
  이력이 있다(오너 표현: "이상한 사이트가 되어버렸다"). **새 시그널은 여러 개를 한꺼번에 붙이지
  말고, 하나를 정의하고 백테스트와 검증까지 끝낸 뒤에만 다음으로 넘어간다** (5장 참고).

## 4. 불변 규칙(invariant)
- 선물 전용. spot 엔드포인트와 데이터 사용 금지 (2장).
- 실거래 코드는 2장의 안전 원칙 4가지 없이 활성화하지 않는다.
- 현재 분석은 여러 지표를 설명 자료로 함께 보여주지만 주문 시그널로 사용하지 않는다.
  주문 단계에서는 하나의 전략을 정의한 뒤 따로 검증한다(3장 이력 참고).

## 5. 설계 결정과 이유 (2026-09-02 분석 도구 구현)
- **채널 baseline·ZigZag 계획은 현재 단계에서 대체됐다**: 자동으로 고점·저점 쌍을 고르는
  규칙을 억지로 확정하지 않고, 선물 확정봉·지표·순매수 흐름을 LLM이 필요할 때 읽는
  툴콜링(tool calling — 모델이 필요한 데이터를 툴로 요청하는 방식) 정보성 분석으로 전환했다.
  이 단계는 주문 실행이나 전략 신호를 만들지 않는다.
- **분석 입력은 불변 멀티 타임프레임 스냅샷으로 고정한다**: 자동 요약과 관리자 질문이
  서로 다른 시각의 캔들을 섞지 않도록 답변마다 `asOfMs`를 함께 보낸다.
- **툴은 읽기 전용 3개로 한정한다**: `getCandles`는 확정봉만, `getIndicatorHistory`는
  RSI·MACD·Supertrend 시계열과 교차 정보만, `getOrderFlow`는 taker buy와 나머지 매도량만
  반환한다. 요청별 호출 상한은 5회다.
- **포지션 데이터는 아직 연결하지 않는다**: 방향·진입가·레버리지·수량·마진 모드가 없으므로
  손절가는 계산하지 않고 기술적 무효화 후보만 설명한다. 향후 포지션 컨텍스트를 붙일 수
  있도록 프롬프트 계약의 확장 지점으로 남긴다.
- **트레이딩뷰 대신 바이낸스 API 직접 연동**: 트레이딩뷰는 임의 조건 자동 실행 API가 없고,
  Pine Script는 순매수/순매도 계산에 필요한 taker buy/sell 분리 볼륨에 애초에 접근할 수 없다
  (총 거래량만 제공). OI·CVD 같은 기본 제공 지표도 있지만 시각적 참고용이고, 정밀한 커스텀
  임계값 계산엔 바이낸스 원본 API가 필요.
- **이전 ZigZag·평행채널 검토는 보류된 역사적 조사**: 스윙 고점/저점은 고정 lookback 봉 개수가 아니라 ZigZag(가격 %) 방식으로 판정하려 했고, "몇 봉
  안에 잡힐지" 문제(40봉이냐 60봉이냐)가 원천적으로 생기지 않는다. 예시 검증(2026-07-01 저점
  $57,800 ~ 2026-08-28 고점 $81,478, 4시간봉, 선물)에서 임계값 7.5% 이상이어야 중간 되돌림
  없이 그 둘만 스윙포인트로 잡혔다 — **임계값은 구간마다 다시 캘리브레이션 필요, 고정값 아님.**
- **평행채널(baseline 저점 2개 + 평행선)도 계산 가능하나, 두 저점의 시간 간격이 중요하다**:
  간격이 좁으면(실측: 12시간) 며칠 뒤로 외삽할 때 오차가 기하급수적으로 커져 무의미한 값이
  나온다(실측: 12시간 간격 저점으로 9일 외삽 후 채널 하단이 $49,212로 붕괴, 현재가와 무관한 값).
  **baseline이 그 구간 내 어떤 캔들에도 하향 이탈되지 않았는지를 검증 조건으로 둔다** — 실제
  지지선이었는지 확인하는 최소한의 필터.
  추세 방향(상승/하락) 판정은 다우이론 방식(최근 고점·저점이 각각 이전보다 높은지/낮은지)을
  ZigZag 결과에 바로 적용해서 구하고, 채널의 baseline을 저점(상승추세)/고점(하락추세) 중 어느
  쪽에 둘지를 그걸로 정한다. 고점·저점 신호가 엇갈리면(혼조) 채널 신호를 내지 않는다.
- **백테스트용 과거 데이터는 내부 DB에 의존하지 않는다**: 바이낸스 선물 REST API가 상장 시점부터
  전체 과거 캔들을 무료·무인증으로 제공하므로, DB 보유 기간이 짧아도 필요한 기간을 그때그때
  API로 받아 쓰면 된다.

## 6. 아직 안 끝난 것 (다음 세션에서 이어감)
- **kline temp 표 정식화(계획만, 미구현)**: `agg_trade_1m_temp`가 설계상 "임시 검증용"인데
  2026-08-31 raw tick 수집 중단 이후 사실상 유일한 실시간 kline 원천이 됐고, DB 집계 없이
  전체 행을 자바로 읽는 구조라 512MB 힙 제약에서 위험하다. 5분봉을 Binance에서 직접 저장
  (1분 롤업 제거) + 롤업 대신 리필(정기적으로 빠진 구간을 스스로 채움) 방식으로 재설계하는
  계획을 `docs/binance/kline-temp-retire-plan.md`에 정리해뒀다(2026-09-03).
  **죽음조건: 이 재설계를 실제로 구현·배포하면 그 계획 문서와 이 항목을 지운다.**
- **포지션 데이터 연동**: 현재는 포지션 방향·진입가·레버리지·수량·마진 모드를 받지 않는다.
  연동 전에는 손절가 계산이나 주문 실행을 추가하지 않는다.
- **전략 검증**: ZigZag와 채널 baseline 자동 선택은 이번 분석 도구로 대체되어 보류됐다.
  나중에 전략으로 되살릴 때는 별도 순수 함수·백테스트·안전 원칙 검증으로 시작한다.
- **운영 관측**: 로컬 LLM 지연·실패, 인터벌별 GAP·STALE·ERROR 전이를 운영 알림과 연결하는
  일은 남아 있다. 현재는 관리자 API 화면에서 상태와 마지막 성공 시각을 보여준다.
- **주문 실행**: 2장의 안전 원칙 네 가지와 최종 안전핀·킬스위치를 먼저 구현하고 검증하기
  전에는 주문 API나 주문 툴을 만들지 않는다.
